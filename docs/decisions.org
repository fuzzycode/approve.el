#+title: Decisions

Each decision has an ID, a status, the decision, and why.  Statuses:
- accepted :: decided; build on it.
- proposed :: our current best answer; confirm or replace when it comes up.
- superseded :: replaced by a later entry (link to it).

Open questions sit at the end.  Decisions that come from [[file:project.org][project.org]] say so.

* Scope
** D01 GitHub only
- Status :: accepted (project.org)
- Decision :: Support github.com and GitHub Enterprise.  No GitLab, Bitbucket, etc.
- Why :: Doing one forge well beats doing several badly.  code-review tried
  several forges and became hard to change ([[file:history.org][history]]).

** D02 Durable state lives on GitHub
- Status :: accepted (project.org)
- Decision :: Everything that matters is stored on GitHub as soon as the user
  commits it: comments, pending reviews, viewed files, resolved threads.  A
  pending review is a real GitHub pending review, not a local draft.  Closing
  Emacs only loses text the user is still typing.
- Why :: Switching between Emacs and the browser is seamless.  pr-review keeps
  pending threads in a buffer-local list, so they are lost when the buffer is
  killed.  code-review kept a local database that had to be synced.

** D03 API-only, never a local clone
- Status :: superseded by [[*D36 No clone needed; a local clone adds to it][D36]] (2026-11-15)
- Decision :: Approve never needs a local clone or worktree.  Diffs come from
  the REST API, and file contents come from GraphQL blobs (or REST contents).
  A local =diff= program may be used on fetched blobs, but never git on a
  checkout.
- Why :: Works for any PR from anywhere, with no setup and no repo state to
  manage.  The cost is no LSP or xref in review buffers; the file view
  ([[file:flows.org::*F15 View the whole file][F15]]) gives syntax highlighting through the file's major mode.

** D36 No clone needed; a local clone adds to it
- Status :: accepted (2026-11-15, by the author; replaces [[*D03 API-only, never a local clone][D03]])
- Decision ::
  - Everything Approve does works through the API alone, from anywhere,
    as in D03: diffs come from the REST API and file contents from GraphQL
    blobs (or REST contents).  A local =diff= program may be used on
    fetched blobs.  A feature that works without a clone never comes to
    need one.
  - When the user has the PR's repository checked out, Approve may use
    the clone for more: what the API can't give, such as the PR's threads
    in the buffers of the files the user edits, or a diff line opened in
    the local file, with LSP and xref.  Without a clone these extras are
    simply absent, never an error, and nothing else changes.
  - The clone holds no review state ([[*D02 Durable state lives on GitHub][D02]]).  Approve reads it (files,
    branch, remotes, git through Magit) and changes it only by a command
    the user gives for that.
  - GitHub's lines are those of the PR's commits; a clone may differ
    (commits not pushed, edits not saved).  An extra that shows GitHub's
    threads in local files maps their lines, and comments only go on
    lines GitHub has ([[*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]).
  - The code that touches a clone lives in its own modules, which the
    core never requires.  How a PR finds its clone (the current project, a
    remote that matches the repository, an option) is decided with the
    first extra that needs it.
- Why :: Reviewing a PR of a project that isn't on the machine must keep
  working with no setup (D03's reason).  But the projects the user works
  on are checked out anyway, and the clone gives what the API can't: the
  user's own buffers, LSP and xref, and review feedback where the code is
  edited, as CLion and VS Code show it.  Keeping the extras apart keeps
  the core testable without git, and every feature usable from anywhere.

** D37 Clones are found where Magit lists them; a commit opens in Magit
- Status :: accepted (2026-11-15, by the author; answers part of what
  [[*D36 No clone needed; a local clone adds to it][D36]] left open, with its first extra)
- Decision ::
  - Approve finds the user's clones in =approve-clone-directories=, a
    list of =(DIRECTORY . DEPTH)= in the format of
    =magit-repository-directories=.  Its default, the symbol =magit=,
    means Magit's list; nil means no clones.  They are listed again
    each time they are needed, as Magit lists repositories.
  - A commit is looked for in every listed clone, in order, and the
    first that has it (=git cat-file -e SHA^{commit}=) is the one.  No
    remote is matched: a sha names one commit anywhere, so this finds
    the PR's commits, a fork's, and those that comments link to in
    other repositories alike.
  - =RET= on a commit (in the commits, the conversation's pushes, a
    comment's commit link) shows it with =magit-show-commit= in that
    clone: Magit's revision buffer, displayed and selected as
    =magit-display-buffer-function= says, with Magit's keys (=q= goes
    back).  When no clone has it, it opens on GitHub as before.
  - The core offers the hook =approve-visit-commit-functions=
    (=approve-nav.el=).  =approve-clone.el= has the function that shows
    the commit, and =approve.el= puts it on the hook, so the core never
    requires the clone module.
  - How a PR, rather than a commit, finds its clone (Phase 7, SP8)
    starts from this option.
- Why :: Magit's revision buffer shows more than a browser (the diff,
  the message, refs, blame from there) and is where later extras can
  go.  Users of Magit set its option already, so they need no setup.
  Asking every clone costs one git call each until one has the commit:
  about 7 ms a clone on the author's machine, a quarter of a second
  before the browser when none of 37 has it.  Matching remotes would ask
  fewer clones but miss commits of other repositories.

** D45 A branch has the PR; its threads are placed by a diff of the text (SP8)
- Status :: accepted (2026-11-16, by the author; answers [[file:roadmap.org::*SP8 The clone and its lines][SP8]] and what
  [[*D36 No clone needed; a local clone adds to it][D36]] left open)
- Found :: On a clone of the scratch repository with four worktrees, on
  #15 (=spike/sp8= into =spike/sp8-base=, threads T1 to T7 on
  =sp8/lines.txt=, T6 made outdated by a later commit) and #16 (the same
  branch into =main=).  Forks were read on magit/magit, without writing.
  Times are from the author's machine (Apple M-series, Emacs 31.1, git
  2.56), with the 37 clones of =~/workspace=:
  - Clones: =magit-list-repos= lists the 37 in 0.7 ms.  That includes
    worktrees inside the listed directories, whose =.git= is a file.
    Their remotes' URLs take 2 ms for all 37, read from each clone's
    =config= file (a worktree's through its =commondir=).  With a git
    call for each clone it takes 200 ms (a git process costs about
    6 ms).  One
    =git for-each-ref --format='%(upstream) %(push) %(worktreepath)'
    refs/heads= (7 to 12 ms) gives every branch of a clone, what it
    tracks and where it pushes, and the worktree that has it checked
    out, wherever that is.  Magit needs git 2.25, and =worktreepath=
    came in 2.23.
  - Remote URLs: 27 of the author's 29 are scp-like
    (=git@github.com:OWNER/NAME.git=) and 2 are https.  =ssh://=, a user,
    a port, and no =.git= occur too.  An SSH host alias
    (=git@github-work:…=) names no GitHub host.  =ssh -G ALIAS= gives
    its =hostname= in 6 ms.  The author's Emacs has
    =magit-repository-directories= nil for now (its new configuration
    hasn't taken Doom's yet), so D37's default finds no clone there.
  - A branch's pull requests: the head repository's
    =ref(qualifiedName: "refs/heads/BRANCH")= has
    =associatedPullRequests=.  It finds every pull request from the
    branch, in any state, into the repository or into its parent: a
    branch of Gleek/magit gives magit/magit#5659.  Once the branch is
    deleted it finds nothing.  =pullRequests(headRefName:)= lists only
    the pull requests into its repository, from any repository:
    magit/magit's =patch-1= gives ten from as many forks.  Asked of the
    head repository and of its parent, it still finds a merged pull
    request whose branch is gone (#14).  All of it fits in one query:
    cost 1, about half a second.  =Commit.associatedPullRequests=
    lists every pull request that contains a commit, not only the ones
    it heads.
  - A branch's head on GitHub: =sp8-ahead= tracks =origin/spike/sp8=,
    and its =@{push}= is empty (=push.default= simple, names that
    differ).  In a triangular setup =@{upstream}= is the base and
    =@{push}= the head.
  - Lines: the file at the pull request's head was diffed against the
    buffer's text, and every thread landed on its own text, in each
    state of the clone.  At GitHub's head, every thread is on its own
    line.  Ahead: a commit not pushed (two lines inserted, T7's line
    changed) and edits not saved (a line deleted, T4's line edited).
    T1 and T2 moved, and T4 and T7 were marked as changed.  Behind (at
    the first head, without the three lines GitHub has at the top):
    every thread moved up three lines.  Diverged (the second commit
    made again, differently): every thread placed.  The state of the
    clone changes only what can be said about it, not the method.
  - The diff's cost, with three lines edited (the prototype was not
    compiled; the process is most of it):
    | File            |   Lines | =call-process-region= | Async, temp files: Emacs busy, hunks |
    |-----------------+---------+-----------------------+--------------------------------------|
    | approve-diff.el |     798 | 2.6 ms                | 3.3 ms, 5.8 ms                       |
    | org.el          |  22 385 | 10.8 ms               | 7.2 ms, 13.3 ms                      |
    | pydevd_cython.c |  52 134 | 24.6 ms               | 2.3 ms, 14.2 ms                      |
    | typescript.js   | 200 276 | 75.1 ms               | 6.9 ms, 40.4 ms                      |
    A change every 50 lines doubles it (183 ms synchronous at 200 000
    lines).  Sending the buffer to the process through a pipe
    (=process-send-region=) blocks Emacs for 0.3 s at 22 000 lines and
    for 3.3 s at 200 000.  =git show OID:PATH=, =git cat-file -e= and
    =git rev-list --left-right --count= take about 7 ms each.
  - Outdated threads: GitHub makes a thread outdated only when its
    lines changed ([[*D41 Suggestions are committed the way GitHub's button does (SP7)][D41]]).  So T6 (=originalLine= 50 at the first head),
    mapped from that commit's file, lands on the line that replaced it,
    marked as changed.  In the worktree still at that commit, it lands
    on its own line.
  - Opening a file: VC already spends 25 ms on =find-file= in a git
    repository (0.6 ms without it).  Finding no =.git= above a file
    takes 0.02 ms.
- Decision ::
  - Clones: [[*D37 Clones are found where Magit lists them; a commit opens in Magit][D37]]'s =approve-clone-directories= alone, with no new option;
    a clone elsewhere is an entry =(DIRECTORY . 0)=.  A clone belongs to
    a pull request when one of its remotes names the base or the head
    repository by host, owner and name (case ignored, =.git= and
    slashes dropped), read from its =config= file.  GitHub's hosts are
    =github.com= and the web host of =approve-api-host=.  Another SSH
    host is resolved by =ssh -G= once a session, so aliases work.
  - A pull request's worktree, among those clones: one whose branch
    pushes to the pull request's head branch in the head repository,
    else one that tracks it (=for-each-ref=, above).  When several do,
    the one that pushes there wins; then Approve asks once and
    remembers for the session.  When none does, Approve says "No clone
    has BRANCH checked out" and offers the file view ([[file:flows.org::*F15 View the whole file][F15]]).  Checking
    a branch out stays a Magit command the user runs.
  - A buffer's clone is its own (its Magit toplevel).  Its branch's head
    on GitHub is the push branch (=@{push}=), else the upstream, else
    the same name on the push remote (=%(push:remotename)=).  That
    remote's URL names the head repository.  A branch on no GitHub
    remote has no pull request, and costs nothing more.
  - A branch's pull requests: one query, as found: the head repository's
    ref's =associatedPullRequests=, and =pullRequests(headRefName:)= on
    the head repository and its parent, kept when their head repository
    is the branch's.  It runs once a session for each repository and
    branch, and again on the user's command.  With several open, the
    one updated last is shown.  A command picks another, remembered for
    the session, and the mode line says "1 of 2".
  - GitHub's lines are those of the file at the pull request's head
    (=headRefOid=).  The file comes from the clone when it has the
    commit (=git cat-file=), else from the API (the file view's cache).
    Approve never fetches into the clone.  The file is diffed against
    the buffer's text, unsaved edits included, with carriage returns
    dropped on both sides.  Both are written to temporary files, and
    =diff-command= runs on them in an asynchronous process.  That
    happens when the buffer's pull request loads or changes head, and
    after edits once Emacs is idle (coalesced; an answer for older text
    is dropped).  Between diffs, the overlays move with the text.
  - A thread on an unchanged line goes under it.  A thread on a changed
    line goes under the line now in its place, marked "edited locally".
    One whose lines were deleted locally goes where they were.
    Comments go only on lines that map unchanged to a line of the pull
    request's diff ([[*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]).  On other lines, Approve says why: edited
    locally, or not in the diff.
  - The clone's state is said, never acted on.  Compared with GitHub's
    head, the branch can be the same (nothing is said), ahead ("N
    commits not pushed"), behind ("GitHub has N commits the clone
    hasn't"), diverged ("the branch and GitHub's differ"), or GitHub's
    head can be missing from the clone ("fetch to compare").  This
    takes one =git rev-list --left-right --count HEAD...OID=, when the
    pull request loads and when =HEAD= moves.
  - Outdated threads are shown where they were: =originalLine= at their
    original commit, mapped the same way (that commit's file from the
    clone or the API).  They go under the line now in their place,
    folded, in the outdated look, saying so.
  - Threads on removed lines go between the lines where the pull
    request removed them.  Its patch maps them onto the head, and the
    diff maps that onto the buffer.  They sit under the line before,
    with the file view's mark for removed lines, folded.  Threads on
    the whole file go at the top of the buffer.
  - Turning it on: the command =approve-feedback-mode= in a buffer, and
    =approve-feedback-global-mode=, off by default.  When it is on, a
    file opened on a branch with an open pull request turns the mode on.
    The command also takes a closed or merged pull request, after
    asking ("#14 is merged: show its threads anyway?").  A pull
    request's store loads in the background, once, shared by its PR
    buffer and the clone's buffers.
- Why ::
  - The remotes tie a clone to GitHub, and reading them from files keeps
    the search instant over many clones.  Git is asked only in the
    clones of the repository.  D37's option is one list, already set
    for Magit; a second list would be a second thing to keep up to
    date.
  - A branch has the pull request, not a clone: two worktrees of one
    clone hold different pull requests.  The ref's
    =associatedPullRequests= knows a fork's pull requests into its
    parent without guessing which remote is the parent.  The query by
    name finds those whose branch is gone.
  - One method for every state: the diff compares text, so commits not
    pushed, edits not saved, a rebase and a branch behind GitHub all
    map the same way, and a thread stays with its code.  The state only
    changes what is said, and the user decides whether to pull or push.
    Never fetching keeps D36's promise: the clone changes only by the
    user's commands.
  - With temporary files and an asynchronous process, Emacs is busy
    under 10 ms even on a 200 000-line file, so the marks keep up with
    typing.  A pipe would block Emacs for seconds.
  - Outdated threads are what a pull request's author fixes; where they
    were, they show what was asked next to the fix.  The same goes for
    removed lines ("why did this go?").
  - Opt-in, because the global mode queries GitHub and loads pull
    requests as files open, and that is the user's choice.  Opening a
    file then costs less than VC already spends: about 14 ms of git for
    the first file of a clone and branch, nothing after.
- Amended (2026-11-16) :: Found writing =approve-clone.el=: git can't
  resolve a =simple= push (its default) to a remote other than the one

- Amended (2026-11-17) :: The author's choice: the PR buffer holds the

- Amended (2026-11-18) :: The author's choice, writing the ways between

- Amended (2026-11-18) :: Found writing the global mode: it turns the

* UI
** D04 Buffers are magit-section trees built from section hooks
- Status :: accepted (project.org)
- Decision :: Every Approve buffer derives from =magit-section-mode=.  Its
  content is a hook of section inserters, named =approve-insert-<name>-section=.
  Users add, remove and reorder sections with =approve-add-section-hook=
  (an alias of =magit-add-section-hook=).
- Why :: Familiar to every Magit user; collapsing, navigation and visibility
  caching come for free; flexible per user.

** D05 One PR buffer by default; split layout optional
- Status :: accepted (2026-11-08); amended 2026-11-18
- Decision :: By default, one PR buffer holds the overview, conversation,
  commits, checks, the file list and the diff.  Diff bodies are collapsed and
  inserted lazily.  =approve-layout= set to =split= moves the diff into a
  linked diff buffer, leaving the file list in the overview.  Both layouts are
  just different section hooks over the same store.
- Amended (2026-11-18, by the author) :: The file list is not in the
  buffer by default, for now: =approve-insert-files-section= stays, and
  =approve-add-section-hook= puts it back before the diff.  The diff's
  headings already list the files, which are viewed and their threads;
  what the list alone shows, each file's size and a count of the
  threads on whole files, is then not in the buffer.  It may be
  removed for good later.
  =j f= goes to the list when the buffer shows it, else to the diff.
  The split layout (Phase 11) decides then what its overview links to
  the diff buffer from.
- Why :: One buffer is simplest to navigate and search.  The split layout
  mirrors GitHub's tabs and Magit's status/diff split, and keeps huge PRs fast.
  Making it a hook choice costs almost nothing.

** D06 Menus are transients; everything is reachable from =?=
- Status :: accepted (project.org); amended 2026-11-15
- Decision :: Every command is reachable from the dispatch transient (=?=).
  Bigger tasks have their own transients: submit review, merge, metadata,
  jump, review range, search filters.  Suffixes that don't apply are shown
  but inapt (=:inapt-if=), based on context and =viewerCan*= fields.
- Amended (2026-11-15) :: The menus list only commands that exist.  A new
  command joins the dispatch, and any other menu it fits, in the change
  that adds it; a test checks that every command bound in a PR buffer is
  reachable from =?=.  A command that changes the PR starts with its
  /preflight/: what it would act on, or a =user-error= saying why it can't
  (nothing it applies to at point, no =viewerCan*=), changing nothing.
  Its =approve-preflight= property names it, and the menus dim the
  command where it would refuse (=approve-action-why-not=), so the menu
  and the command never disagree.
- Why :: Discoverability, Magit consistency, and one place to learn the keys.

** D11 Show bodyHTML; edit markdown
- Status :: accepted
- Decision :: Descriptions and comments are displayed from GitHub's
  =bodyHTML=, rendered with =shr= and custom tag handlers (code blocks with
  syntax classes, suggestion blocks, tables, task lists, blockquotes, details,
  images).  Editing uses the raw markdown =body= in a =gfm-mode=-derived input
  buffer.
- Why :: GitHub's HTML already resolves mentions, issue links, emoji, and
  suggestion diffs, so we render exactly what the browser shows.  approve-v2
  proved the shr approach works (=approve-ui-html.el=).

** D12 Own diff parser and renderer
- Status :: accepted
- Decision :: Parse unified patches ourselves and insert file, hunk and line
  sections directly.  Don't wash diffs through =magit-diff-wash-diff= with
  =cl-letf= overrides.
- Why :: approve-mvp and approve-old overrode Magit internals, which was
  fragile and fought Magit's section painting.  approve-v2's own renderer was
  simpler and let threads live inside the diff.

** D16 Own faces and one icon abstraction
- Status :: accepted (project.org)
- Decision :: All faces live in =approve-faces.el= and inherit from Magit or
  built-in faces.  All icons go through =approve-icon= (semantic name →
  nerd-icons glyph, or a Unicode fallback when =approve-use-nerd-icons= is nil
  or the font is missing).  Which glyphs: [[*D31 Icons come from Material Design][D31]].
- Why :: Themes work out of the box; users can restyle everything; terminals
  and machines without the font still look right.

** D17 Evil is supported, never required
- Status :: accepted (project.org)
- Decision :: Evil bindings are defined in =approve-evil.el=, loaded with
  =with-eval-after-load 'evil=.  In normal state we never shadow motions or
  visual selection ([[file:ui.org::*Keys][keys]]).
- Amended (2026-11-08) :: package-lint rejects =with-eval-after-load= in a
  package, so =approve-pr-mode= requires =approve-evil= when evil is loaded
  (=featurep=), before evil sets the buffer's keymaps up.  The rest stands.
- Why :: The author uses evil; many users don't.  Visual line selection is how
  evil users pick a range of lines to comment on.

** D22 Comments go into the pending review by default
- Status :: proposed
- Decision :: =c= on code adds to the pending review, starting one if needed
  (GitHub's "Start a review").  =C-u c= posts a single comment right away
  (GitHub's "Add single comment") when no review is pending.  When a review is
  pending, every code comment and reply joins it, as on GitHub.
  =approve-comment-default= (=review= or =single=) flips the default.
- Amended (2026-11-13) :: GitHub refuses a single comment while a review
  is pending ([[*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]).  Then =C-u c= says so in the input's header line,
  and the comment joins the review.
- Why :: Batching comments into one review is how code review is meant to work
  and sends one notification.  Matches pr-review's habit, but on GitHub's side
  ([[*D02 Durable state lives on GitHub][D02]]).

** D26 Icons come from Codicons
- Status :: superseded by [[*D31 Icons come from Material Design][D31]] (2026-11-09)
- Decision :: =approve-icon= maps every semantic icon to the Codicons set in
  nerd-icons (=nerd-icons-codicon=, names =nf-cod-*=).  The mapping is the
  table in [[file:ui.org::*Icons][ui.org › Icons]].  It is a =defcustom= (=approve-icons=), so

- Why :: Compared side by side with Material Design, Font Awesome and
  Octicons ([[file:html/icons.html][html/icons.html]]); Codicons cover every pull request state
  (open, draft, merged, closed, request changes, comment draft) with one
  consistent outline style.  No extra dependency: nerd-icons ships them.

** D31 Icons come from Material Design
- Status :: accepted (2026-11-09, replaces [[*D26 Icons come from Codicons][D26]]); amended 2026-11-15
- Decision :: =approve-icon= maps every semantic icon to the Material Design
  set in nerd-icons (names =nf-md-*=), as in the table in [[file:ui.org::*Icons][ui.org › Icons]].
  =approve-icons= stays a =defcustom=, and it takes a glyph from any
  nerd-icons set: the prefix of the name (=nf-md-=, =nf-cod-=, =nf-oct-=,
  =nf-fa-=, …) picks the set.  Reactions are icons too (=reaction-thumbs-up=
  … =reaction-eyes=): flat outline glyphs like the rest, with GitHub's colour
  emoji only as their fallbacks.
- Why :: In Emacs, Codicons' pull request, merge and comment glyphs look
  like GitHub's Octicons, which the author finds ugly next to text.  Of the
  four sets compared ([[file:html/icons.html][html/icons.html]]), the author chose Material Design's
  rounded outline icons, which cover every state too (pull, merge, branch
  removed, a progress pencil for drafts, decagrams for verdicts).  Colour
  emoji for reactions looked out of place next to them.
- Amended (2026-11-15) :: Drafts take Codicons' pull request draft
  (=nf-cod-git_pull_request_draft=), the glyph gh-dash draws them with,

    and nothing else, so typing doesn't repaint.

    them.  =zo= unfolds them, and =zc= folds them; when they are
    already as the key wants them, or the line has none, the key does
    what it does without the mode, so a second =zc= folds the code.
    =zO= and =zC= do both at once, as vim's fold every fold at point.
    The key passed on only matters when nothing was done to the
    threads: when they were, its error is dropped.  Only the mode's
    keys are passed on, never =M-x=.
  - =zR= and =zM= unfold and fold every thread of the file, and leave
    the code's folds alone; =zr= and =zm= are left to the buffer's own
    folding, which the mode doesn't bind.  In a file without threads,
    =zR= and =zM= do what they do without the mode.
  - =]t= and =[t= leave the threads they unfold unfolded.
- Why :: Folds nest in vim: =zc= closes the innermost fold at point, then
  the next, and =zo= opens them the other way.  Threads under a line
  are the innermost thing there, so the keys reach the code after them,
  never instead of them.  A fold that hides feedback should say so, as
  a closed fold in an IDE keeps its gutter marks; the bubble is where
  the eye already looks.  Threads drawn after the text they belong to
  can't stay under a line that isn't shown, and a jump that lands in a
  fold must open it, or it lands nowhere.  Separate keys for every
  thread (=zR= =zM=) and every fold of code (=zr= =zm=) let the user
  fold the code and keep the feedback open, or the other way.

** D53 A pull request is fetched into its clones on the user's command
- Status :: accepted (2026-11-20, by the author, who asked for it; he
  chose GitHub's ref into =refs/pullreqs/=, every clone, no key, and a
  message when there is no clone)
- Decision ::
  - =approve-fetch-pull-request= fetches a pull request's commits into
    the user's clones, so that they are found there: =RET= on a commit
    shows it in Magit ([[*D37 Clones are found where Magit lists them; a commit opens in Magit][D37]]), and the feedback mode compares the clone
    with GitHub's head and reads GitHub's text from it ([[*D45 A branch has the PR; its threads are placed by a diff of the text (SP8)][D45]]).
  - What: GitHub's ref of the head on the base repository,
    =refs/pull/N/head=, into =refs/pullreqs/N=, forced:
    =git fetch REMOTE +refs/pull/N/head:refs/pullreqs/N=.  GitHub has it
    for every pull request, a fork's and one whose branch is deleted
    too, and the ref keeps the commits from git's garbage collection.
    =refs/pullreqs/= is where Forge fetches pull requests, so the two
    agree.  No branch changes, local or remote-tracking.
  - Where: every clone of =approve-clone-directories= with a remote that
    names the base repository (D45's matching of remotes), once for
    each git directory, as a clone's worktrees share it; from the first
    such remote.  A clone with only the fork as a remote has no such
    remote, and is passed by.
  - How: in the background, through Magit's processes, as
    =magit-git-fetch= runs git: credentials asked for, git's output in
    Magit's process buffer (=$=), the clone's Magit buffers refreshed
    after.  No buffer is saved first: a fetch changes no file.  The echo
    area says "Fetching #N into ~/src/x...", then "Fetched #N into
    ~/src/x, as refs/pullreqs/N", or git's error for each clone it
    could not fetch into.  The feedback mode's buffers of the pull
    request then compare their clone with GitHub's head again.
  - Without a clone of the repository, the echo area says so ("No clone
    of OWNER/NAME in approve-clone-directories: nothing fetched"), and
    nothing else happens: no error, no beep.
  - No key: =M-x=, and =U= in the dispatches of the PR buffer, the file
    view and the feedback mode.  The command is in =approve-feedback.el=,
    which arranges the clone's commands in the core's buffers; the git
    part is in =approve-clone.el= ([[*D36 No clone needed; a local clone adds to it][D36]]).
  - Approve still fetches nothing by itself (D45, amended): a fetch is
    a command the user gives, as D36 allows.
- Why :: Without a pull request's commits in the clone, =RET= on a commit
  went to the browser and the feedback mode said "fetch to compare".
  Fetching by hand needs the pull request's ref, which few remember,
  and a fork's branch has no remote in the clone.  GitHub's ref works
  for every pull request through the remote the clone has, and a ref
  of its own leaves the user's branches alone.  Every clone gets the
  commits, since D37 asks every clone for a commit and a buffer's
  clone may be any of them.

** D07 ghub, wrapped by approve-api
- Status :: accepted (project.org)
- Decision :: All network calls go through =approve-api.el=, which wraps
  =ghub-graphql= and =ghub-request=.  Calls are async only, with a timeout, a
  progress reporter, error classification, and callbacks run in the
  originating buffer (skipped if it has died).
- Why :: ghub handles auth (auth-source), hosts, and Enterprise.  One wrapper
  gives one place for timeouts, logging and tests to mock.

** D08 GraphQL files with fragment includes
- Status :: accepted
- Decision :: Queries, mutations and fragments live in =graphql/= as
  =.graphql= files.  =${include:fragments/x.graphql}= pulls in a fragment;
  includes are resolved recursively, deduplicated, and checked for cycles.
  Every selected object with an =id= also selects =__typename=.  Mutations
  return the changed object through the same fragments the queries use.
- Why :: One shape per type, so the store can patch any response.  The files
  are reusable in GraphQL tools (Altair, =verb=) during development.

** D09 REST only where GraphQL can't do it
- Status :: accepted
- Decision :: Use REST for patch text (=GET /repos/{o}/{r}/pulls/{n}/files=,
  paginated, at most 3000 files), commit-range compares
  (=GET /repos/{o}/{r}/compare/{a}...{b}=), notifications (=/notifications=),
  and markdown preview (=POST /markdown=).  Everything else uses GraphQL.
- Why :: GraphQL has no patch text and no notifications.  Per-file patches
  page well and let large PRs render progressively.

** D10 Normalized, buffer-local store
- Status :: accepted
- Decision :: Responses are normalized into a buffer-local store keyed by
  =__typename= and =id=, with refs between entities.  GraphQL connections are
  unwrapped, but their =totalCount= and =pageInfo= are kept.  Mutation
  responses are patched in through the same normalizer.  Creations and
  deletions also need explicit list edits (append or remove a ref).
- Why :: Partial mutation responses update every place an entity appears.
  approve-v2's =approve-model.el= proved it, and it can be reused with small
  additions.

** D14 No optimistic updates
- Status :: accepted
- Decision :: The UI changes after GitHub confirms.  While waiting, the target
  shows an in-flight mark (face and spinner text).  On failure the mark clears,
  the error is shown, and any typed text is kept for a retry.
- Why :: Simple, always true to GitHub ([[*D02 Durable state lives on GitHub][D02]]), no rollback code.  Network
  latency is acceptable (project.org, "Fast").

** D15 Mutations are serialized; queries run in parallel
- Status :: accepted
- Decision :: Mutations go through a FIFO queue, one at a time.  Queries run
  concurrently.
- Why :: GitHub's secondary rate limits punish bursts of mutations, and order
  matters (create the review, then add threads).  approve-old had a queue for
  the same reason.

** D32 Reviews are written the way GitHub's API allows (SP1)
- Status :: accepted (2026-11-13, answers [[file:roadmap.org::*SP1 Review API behaviour][SP1]] and Q3, except the
  commit-range view)
- Found :: With =gh api graphql= on the scratch repository
  (fuzzycode/test-approve: #8 is the viewer's own pull request, #9 one by
  github-actions[bot]):
  - =addPullRequestReviewThread= with the =pullRequestId= (no review id)
    adds the thread to the viewer's pending review, and starts one when
    there is none.  A file-level thread takes =subjectType: FILE= and no
    line.
  - While a review is pending, =addPullRequestReview= is refused, with or
    without an event: "User can only have one pending review per pull
    request".  No single comment can be posted then.
  - A reply (=addPullRequestReviewThreadReply= without
    =pullRequestReviewId=) joins the pending review when there is one, and
    is published at once (as a review of its own) when there is none.
  - A range may run from a removed line to an added one, or the other way.
    GitHub even takes a range across hunks.  A line outside every hunk, or
    a range starting outside one, takes no comment: the answer is
    =thread: null=, with no error.
  - Deleting the last comment of a pending review deletes the review.  An
    empty pending review made on purpose (=addPullRequestReview= with
    nothing) stays.
  - Discarding a pending review (=deletePullRequestReview=) removes its
    threads and comments, but a query right after may still list them.
  - Comment and Request changes need a body or at least one comment;
    Approve needs neither.  For an empty Comment, GitHub's message is empty
    or speaks of requested changes.  On the viewer's own pull request,
    Approve and Request changes are refused ("Can not approve your own pull
    request").
  - =submitPullRequestReview= takes the =pullRequestId= alone.
  - A pending review keeps a body given when it was made
    (=addPullRequestReview= with =body= and no event); =updatePullRequestReview=
    edits it, and a submit without a body keeps it.  A pending review without
    a body can't get one ("Could not edit a review with a missing body").
  - A one-line thread's =startLine= is not null: it repeats the line, or for
    a context line on the LEFT gives its new number; its =startDiffSide= is
    null.  A file-level thread has =line= 1.  A comment's =startLine= is null
    for one line.
- Decision ::
  - Code comments and replies are sent with the pull request's id, never the
    review's: GitHub finds the pending review or starts one ([[*D22 Comments go into the pending review by default][D22]]).  A
    single comment is =addPullRequestReview= with =event: COMMENT=, only when
    nothing is pending; a single comment on a whole file is a file thread
    then a submit (two mutations, queued).
  - A range stays in one hunk, and only diff lines that are drawn take
    comments: the lines between hunks are not shown, and a suggestion over
    them would replace code nobody read.  A =null= thread is a failure, with
    Approve's own message.
  - Submitting checks first: Comment and Request changes need a body or
    comments, and on the viewer's own pull request (=viewerDidAuthor=)
    Approve and Request changes are inapt.  Submit and discard use the pull
    request's id.
  - Deleting the last pending comment drops the pending review from the
    store.  Discarding removes its threads and comments by list edits, not
    by a query.
  - The review body draft is an input draft in the session; the body input
    starts from it, else from the pending review's body.
  - A thread is a range only when its =startDiffSide= is set; file-level
    threads are known by =subjectType=, never by =line=.
- Why :: These are GitHub's rules.  Checking them before sending gives
  clear messages where GitHub's are silent or misleading.  Leaving the
  pending review to GitHub means a review started in the browser is
  continued without Approve knowing its id.

** D35 Mutations keep the store true: GitHub's answer, then list edits
- Status :: accepted (2026-11-14, by the author)
- Decision :: Each mutation function in =approve-mutations.el= queues its
  mutation and, once GitHub has answered, makes the store true by itself;
  commands never edit the store.
  - It patches the store with the changed object GitHub returns, through
    the fragments the queries use ([[*D08 GraphQL files with fragment includes][D08]]).
  - The mutations that change the PR's review state (a thread, a reply, a
    review added or submitted) also select that state on their pull
    request: one fragment, =PullRequestReviewStateFields= (review
    requests, latest verdicts, review decision, the viewer's latest and
    pending review), which the core query spreads too.  So whether a
    review is pending, and with which comments, is GitHub's word.
  - It makes the list edits that follow from the answer: a new thread
    joins the PR's threads, a reply its thread, a submitted review and a
    conversation comment the conversation.
  - A deletion is list edits alone, as GitHub may still list what was
    deleted right after ([[*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]): a deleted comment leaves its thread,
    a thread left empty leaves the PR, a pending review left without
    comments (or discarded) leaves it with its comments.
  - It calls its callback with the ref of the entity it changed, and its
    errorback with an approve-api error, also when GitHub answers without
    an error but made no change (=approve-mutation-refused=, such as a
    null thread).  An action's =:done= is left for what is not the
    store's.
- Amended (2026-11-14) :: Found on the scratch repository by
  =dev/scratch.el=, which runs every mutation on PR #8 and compares the
  store with the PR loaded anew:
  - GitHub's timeline never lists a review that holds a reply alone (one
    a reply published at once makes), though =reviews= does.  Such a
    review stays out of the store's conversation.
  - Deleting the last comment of a review without a body deletes the
    review, submitted or pending; a review with a body stays.  So a
    deleted comment also leaves its review's =commentCount=, and a review
    left with neither comments nor a body leaves the PR's lists.
  - Right after a discard, a query can still list the review for a few
    seconds ([[*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]); the list edits are right at once.
- Why :: A list edit follows from what GitHub did, not from the command
  that asked: a reply joins its thread whichever key sent it.  In the
  operations layer, next to the queries that load the same lists, the
  store's layout stays out of the commands, as the selectors keep it out
  of the renderers.  Asking GitHub for the review state, rather than
  tracking it by hand, finds a pending review started in the browser and
  costs one nested selection; deletions can't ask, because GitHub's answer
  may be stale then.

    Pull and try again."
  - Not found: whether =createCommitOnBranch= writes to a fork's branch

    side (=diffSide= RIGHT, and =startDiffSide= RIGHT or null) that is

  - Applying one or a batch: the files at the store's =headRefOid=

    its block, from the bottom up; the file keeps its line endings and its
    final newline or lack of one.  Then one =createCommitOnBranch= on the
    head repository's branch with =expectedHeadOid= the store's head,
    then =resolveReviewThread= for each thread, then the PR loaded again.

  sees no difference in the history, and the thread ends resolved either

  a push made since.  Checking first gives GitHub's own messages, which
  the API never sends since it knows nothing of suggestions.

  group: right after =createCommitOnBranch=, the pull request's

  once a second, ten times at most, until it is the new commit, and
  loads the PR then (=approve-query-await-head=).

  - =updatePullRequestBranch= (=MERGE= or =REBASE=) answers with the head
    as it was; GitHub moves it a second or two later.  A stale
    =expectedHeadOid=: "head sha didn't match the current head ref."
    =viewerCanUpdateBranch= stayed false on branches behind their base
    while the update worked: it follows the repository's "Always suggest
    updating pull request branches" (=allowUpdateBranch=), off there.
  - =viewerCanDeleteHeadRef= is false while the pull request is open,
    and true once it is merged or closed.  =deleteRef(refId)= deletes the
    branch (GraphQL: no REST is needed, [[*D09 REST only where GraphQL can't do it][D09]]); the PR's =headRef= is
    null then.
  - Auto-merge and merge queues can't be tried there: the repository
    doesn't allow auto-merge ("Auto merge is not allowed for this
    repository"), and merge queues need an organization ("Merge queues
    are not enabled for fuzzycode/test-approve.").
- Decision ::
  - =m= merges with a merge commit, =s= squashes, =r= rebases, in the
    merge menu ([[file:ui.org::*Merge / state (=m=)][ui.org]]).  =m= and =s= write the commit message in an
    input buffer, starting from GitHub's, asked for when the command runs
    (it changes with each push): its first line is the title, the rest
    the body, which is sent empty when it is.  =C-c C-c= merges; the
    input is the confirmation.  =C-u m= and =C-u s= merge with GitHub's
    message after =y-or-n-p=, as =r= does (it has no message).
  - Before anything is sent, merging needs: an open pull request (GitHub
    would merge a closed one), not a draft, a method the repository
    allows, the right to write to it (=viewerPermission= =WRITE=,
    =MAINTAIN= or =ADMIN=), no conflicts (and =canBeRebased= for =r=),
    GitHub done working it out (not =UNKNOWN=), no merge queue (=Q=), and
    a =mergeStateStatus= that allows it: =CLEAN=, =UNSTABLE= or
    =HAS_HOOKS=.  =BLOCKED= and =BEHIND= only for a viewer who may bypass
    the rules (=viewerCanMergeAsAdmin=), and the input and the question
    say it bypasses them.  The merge is of the head the store holds
    (=expectedHeadOid=).
  - =-d= deletes the head branch after the merge, when GitHub's answer
    says the viewer may (=viewerCanDeleteHeadRef=).  It is off by default
    (=C-x s= in the menu saves it on) and dimmed where the repository
    deletes merged branches itself.  =k= deletes the branch of a merged
    or closed pull request, as GitHub's button does.
  - =a= enables auto-merge: it asks for the method among those allowed,
    the viewer's default first (not when there is only one), then the
    message as =m= and =s= do.  It is dimmed without
    =viewerCanEnableAutoMerge=, and =x= (disable) without
    =viewerCanDisableAutoMerge=.  =Q= adds the pull request to the merge
    queue, or takes it out, where the base has one (=isMergeQueueEnabled=).
  - =u= merges the base into the head branch and =U= rebases it on the
    base, after =y-or-n-p=, from the head the store holds; both where the
    pull request is open and the viewer may push to its branch
    (=viewerCanUpdateBranch=, or =viewerCanEditFiles=, as the first
    follows a setting).  The PR loads again once GitHub's head moved
    (=approve-query-await-head=).
  - =c= closes the pull request, or reopens it (=viewerCanClose=,
    =viewerCanReopen=; a merged one stays merged), after =y-or-n-p=.  =D=
    is F12's draft or ready.
  - A merge loads the PR again, as =g= does: its conversation, commits
    and header all change.  The other mutations answer with
    =PullRequestMergeStateFields=, which the core spreads too, and the
    store is patched with it ([[*D35 Mutations keep the store true: GitHub's answer, then list edits][D35]]); the events they add to the
    conversation come with the next load, as the metadata's do.
  - The menu's title line is GitHub's merge box in one line: conflicts,
    checks, reviews, =BEHIND=, auto-merge, the queue; or who merged it.
    It says "behind" without a count: GitHub gives the count only by
    comparing the two branches by name, one more query per load.
- Why :: The commit should read as GitHub's would, and the message is
  GitHub's own until the user changes it, as in the browser.  GitHub's
  API is laxer than its merge box (a closed pull request merges) and its
  messages are terse ("Pull Request is not mergeable"), so Approve says
  what stands in the way, and which key helps, before sending; the
  menu dims the same (D06).  The head the user read is the head merged.

* Rendering
** D13 Full redraw, point restored by section ident
- Status :: accepted (revisit if measurements say so)
- Decision :: After data changes, the buffer is erased and the section hook
  re-run.  Point is restored to the same section (by =magit-section-ident=)
  and the same line offset within it.  Collapsed/expanded state is kept by
  magit-section's visibility cache, so every section needs a stable value
  (never =(random)=, which approve-v2 used for diff lines).  Redraws are
  coalesced (≈50 ms) while several responses arrive.
- Why :: Partial redraws in magit-section are hard and bug-prone.  With lazy
  diff bodies, full redraws stay cheap.  Measure in Phase 1; optimize only if
  needed.

** D28 Diff line numbers are text that copying leaves out
- Status :: accepted (2026-11-08, answers Q1)
- Decision :: Each diff line starts with its old and new line numbers and
  its =+=/=-= marker, as text.  That text has the property
  =approve-decoration=, and Approve buffers filter copied text
  (=filter-buffer-substring-function=, so =M-w= and evil's =y=) through
  =approve-render-strip-decorations=, which drops it: copying diff lines
  gives the code alone.  =approve-diff-line-numbers= turns the numbers off.
  Other gutters (thread bars, indentation, the timeline line) are
  decoration text too (=approve-render-prefix=), with a =wrap-prefix= so
  wrapped lines continue under their text.
- Amended (2026-11-09) :: indentation and gutters were display-only
  =line-prefix=.  A collapsed section lent its hidden body's prefix to the
  next heading, which showed indented, and a move down to column 0 stopped
  on that prefix inside the hidden text.  As text, they behave like Magit's
  own indentation; the prefix takes its line's section, diff line and thing,
  so commands work on it as on the line.
- Why :: Text matches the mockups, is indented with its section, works in
  terminals and costs nothing extra to draw.  A margin would sit at the
  window's edge, need its width managed per window, and still put a real
  character on each line; overlays for 20 000 lines would be slow.

** D30 Diff hunks are syntax-highlighted by default
- Status :: accepted (2026-11-08, answers SP4 and Q2)
- Decision :: =approve-diff-fontify= is t by default.  When a file is first
  expanded, its new side (context and added lines) and old side (removed
  lines) are fontified as two texts in a temporary buffer in the major mode
  =auto-mode-alist= gives its path, with the mode's hooks delayed (never
  run).  The syntax colours go over the diff backgrounds.  Results are
  cached per patch, so redraws and later expansions reuse them.
- Why :: GitHub colours diffs, and diff-mode does the same by default
  (=diff-font-lock-syntax=).  Measured on 500 lines, compiled: elisp 1.2 ms,
  Go 3.8 ms, JavaScript 5.8 ms, C 9.5 ms, Python 12.3 ms, paid once per file
  on top of 16 ms to draw it, within the 30 ms budget.  Expanding all 300
  files of the large fixture went from 2.1 to 6.1 ms per file, mostly the
  set-up of a mode per file.  Collapsed files cost nothing.

** D47 Files are split by concern, never by length
- Status :: accepted (2026-11-17, by the author)
- Decision :: A module holds one concern, whatever its length.  Code that
  belongs together stays in one file, however long it grows; a file is
  split only when it holds two concerns, each then in its own module.
  Length is never a reason to split, or to put new code elsewhere: new
  code goes in the module of its concern.  This replaces the earlier rule
  of thumb, "split a file when it passes ~600 lines".
- Why :: A concern split across files for length is harder to read and
  change than one long file, and an arbitrary line count puts code where
  it doesn't belong.  Writing =approve-lines.el= (Phase 7), the line
  count of =approve-clone.el= was weighed as a reason for a new file;
  the author ruled it out: what belongs together stays together.

** D49 Released from GitHub first; MELPA once there is interest
- Status :: accepted (2026-11-17, by the author)
- Decision :: The first release (Phase 8) is a tagged version on GitHub,
  installed from the repository: =package-vc-install= (with =:lisp-dir=
  =lisp=), =use-package='s =:vc=, straight or elpaca, as the README shows.
  Approve is not submitted to MELPA then.  Once it has been used in the
  wild and there is interest, it may be, with a new decision.  Until
  then the code stays as MELPA would take it: =make lint= keeps
  package-lint and checkdoc clean.
- Why :: Approve should be tried and judged by its first users before it
  is offered to everyone: a release from GitHub reaches the people who
  look for it, and changes can still be made freely.  A package on MELPA
  is a promise to maintain it for many, worth making once there is
  interest.  Keeping lint clean costs little and leaves the way open.
