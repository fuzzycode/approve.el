#+title: Flows — user scenarios

Each scenario (F01…) says who does what, then shows it as a flowchart.  The
notation is the same throughout:

#+begin_example
 ┌──────────┐
 │ action   │   something Approve does
 └──────────┘
 ◇ test? ◇      a decision; branches are labelled
 [user]         something the user does
 ──▶            flow
 ⇢ F07          continue in another flow
#+end_example

show only what differs.  Keys are from [[file:ui.org::*Keys][ui.org]].  Mutations are named in
[[file:architecture.org::*API map][architecture.org]].

* F00 The action pipeline
Every command that changes something on GitHub runs this pipeline.  Code
lives in =approve-actions.el=; each command supplies the parts marked ✱.
Its mutations (=approve-mutations.el=) patch the store with GitHub's answer
and make the list edits that follow from it ([[file:decisions.org::*D35 Mutations keep the store true: GitHub's answer, then list edits][D35]]), so a command never
edits the store itself.

#+begin_example
 [user] key or menu suffix
        │
        ▼
 ┌─────────────────────────────────────┐
 │ ctx = approve-context-at-point      │
 └──────────────────┬──────────────────┘
                    ▼
        ◇ ✱ does the command apply to ctx? ◇──no──▶ user-error saying what it needs
                    │ yes                           ("Put point on a thread")
                    ▼
        ◇ ✱ viewerCan… / not locked? ◇────────no──▶ user-error saying why not
                    │ yes
                    ▼
        ◇ ✱ needs text? ◇──yes──▶ open input buffer (draft prefilled)
                    │ no                    │
                    │            [user] C-c C-k ──▶ keep draft, restore windows, stop
                    │                       │
                    │            [user] C-c C-c
                    ◀───────────────────────┘
                    ▼
 ┌─────────────────────────────────────┐
 │ mark target in flight (face, ⟳)     │
 │ ✱ enqueue mutation(s)  (serial)     │
 └──────────────────┬──────────────────┘
                    ▼
        ◇ success? ◇──no──▶ clear mark · show GitHub's message · keep draft
                    │ yes                 (rate limit: queue pauses until reset)
                    ▼
 ┌─────────────────────────────────────┐
 │ patch store with returned fragment  │
 │ list edits (append/remove refs)     │
 │ clear draft · clear mark            │
 │ redraw (all buffers of this PR),    │
 │ restore point                       │
 └─────────────────────────────────────┘
#+end_example

* F05 Comment on code
The heart of reviewing.  It works on one line, a range (region or visual
line selection), or a whole file.

#+begin_example
 [user] c  (C-u c = single comment)
        │
        ▼
     ◇ region active? ◇──yes──▶ start = first diff line in region
        │ no                     end   = last diff line in region
        │                              │
        │                   ◇ same file and hunk, ◇──no──▶ user-error
        │                   ◇ all lines in diff?  ◇        "A range must stay in one hunk"
        │                              │ yes
        ▼                              │
     ◇ on a diff line? ◇──yes──▶ target LINE (path, side, line)
        │ no                           │
        ▼                              │
     ◇ on a file heading? ◇──yes──▶ target FILE (subjectType FILE)
        │ no                           │
        ▼                              │
        ⇢ F10 (conversation comment)   │
                                       ▼
 ┌────────────────────────────────────────────────────────┐
 │ highlight target lines · open input buffer             │
 │ header: "Comment on approve-api.el:41–42 · pending…"   │
 └───────────────────────────┬────────────────────────────┘
                             │ [user] C-c C-c
                             ▼
     ◇ single comment (C-u, or default single)? ◇──no──────────────────┐
        │ yes                                                          │
        ▼                                                              │
     ◇ viewer has a pending review? ◇──yes──▶ joins it (the header     │
        │ no                                    line said so) ────────▶│
        ▼                                                              ▼
 addPullRequestReview                            addPullRequestReviewThread
 (event COMMENT, threads [target])               (pullRequestId, target, body)
 → published now; a whole file:                 → joins the pending review,
   a file thread, then submit                      or starts one (D32); a null
        │                                          thread fails ("that line takes
        │                                          no comment"), draft kept
        ▼                                                              ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ patch store: thread, comment, review, the PR's review state         │
 │ append thread ref to PR.reviewThreads                               │
 │ pending review: as GitHub's answer has it (new or not, D35)         │
 │ redraw: thread under its line, "Your pending review", counts        │
 └─────────────────────────────────────────────────────────────────────┘
#+end_example

Side and line rules:
- Added and context lines take =side RIGHT= and the new line number.  Removed
  lines take =side LEFT= and the old line number.
- A range spanning removed and added lines uses =startSide=/=side= for each
  end.
- The thread is drawn under the =line= (the end of the range).
- A range stays in one hunk, and only lines of the diff take comments
  ([[file:decisions.org::*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]): GitHub would take a range across hunks, but the lines between
  them aren't shown, and it answers a line outside the hunks with a null
  thread, not an error.

The pending review over its life:
#+begin_example
                first code comment or reply (not single)
   ┌───────┐ ─────────────────────────────────────────▶ ┌─────────┐
   │ none  │                                            │ PENDING │◀─┐ add · edit ·
   └───────┘ ◀─── discard: deletePullRequestReview ──── └────┬────┘──┘ delete comments
       ▲        (or delete its last comment, D32)            │
       │          submit: submitPullRequestReview            │
       └──────────── (APPROVE · REQUEST_CHANGES · COMMENT) ◀─┘
                     review becomes visible to everyone

 A pending review started in the browser is found on load (Q core)
 and continued here, and the other way round.
#+end_example

* F08 Edit or delete own text
=e= edits and =k= deletes whatever own text is at point.  The context decides
the mutation.  The title is in the header line, never at point: =t= edits it
from anywhere, and =d= the description.

| Context         | Edit (=e=)                                    | Delete (=k=)                             |
|-----------------+-----------------------------------------------+------------------------------------------|
| title (=t=)     | =updatePullRequest(title)=, single-line input | —                                        |
| description     | =updatePullRequest(body)= (=d= too)           | —                                        |
| issue-comment   | =updateIssueComment=                          | =deleteIssueComment=                     |
| review-comment  | =updatePullRequestReviewComment=              | =deletePullRequestReviewComment=         |
| review (body)   | =updatePullRequestReview=                     | — (dismiss is a separate command)        |
| pending comment | =updatePullRequestReviewComment=              | =deletePullRequestReviewComment= (the    |
|                 |                                               | last one takes the pending review along) |

#+begin_example

* F13 Merge, close, reopen, draft, update branch
As GitHub's merge box, checked first ([[file:decisions.org::*D42 Merging as GitHub's merge box does, checked first (F13)][D42]]).  Code lives in
=approve-merge.el=; the menu is =approve-merge= in =approve-menus.el=.

#+begin_example
 [user] m  (evil: gm)
   │
   ▼
 transient; title line: the merge box in one line (conflicts, checks, reviews,
 behind, auto-merge, queue) · only methods the repository allows · a command
 is dimmed where it would refuse
   │
   ├── m / s / r (method) ──▶ ◇ can it merge now? ◇──no──▶ user-error with the reason and the key
   │                            │ yes                       that helps: closed (c), draft (D),
   │                            │ (BLOCKED or BEHIND only   conflicts, UNKNOWN (g), BLOCKED (a),
   │                            │  for one who may bypass)  BEHIND (u), a merge queue (Q)
   │                            ▼
   │                ◇ m or s, and no C-u? ◇──yes──▶ GitHub's message for the method
   │                            │ no                (viewerMergeHeadlineText / BodyText)
   │                            ▼                              │
   │   ◇ y-or-n-p "Squash and merge #1234 into main?" ◇        ▼
   │          │ no ──▶ stop     │ yes        input "Squash and merge #1234 into main"
   │                            │            [user] C-c C-c (C-c C-k: draft kept, stop)
   │                            ◀──────────────────────────────┘
   │                            ▼
   │                mergePullRequest(method, title, body, expectedHeadOid)
   │                            ▼
   │                ◇ -d and viewerCanDeleteHeadRef? ◇──yes──▶ deleteRef(headRef)
   │                            │ no                                │
   │                            ◀───────────────────────────────────┘
   │                            ▼
   │                load the PR again (F17 "g")
   │
   ├── a auto-merge ──▶ the method (completing-read, your default first)
   │                    → the message as for m / s → enablePullRequestAutoMerge → patch
   ├── x ─────────────▶ disablePullRequestAutoMerge → patch
   ├── Q merge queue ─▶ y-or-n-p → enqueuePullRequest / dequeuePullRequest → patch
   ├── u / U ─────────▶ y-or-n-p → updatePullRequestBranch(MERGE / REBASE, expectedHeadOid)
   │                    → wait for GitHub's head to move → load the PR again
   ├── D draft ───────▶ F12: convertPullRequestToDraft / markPullRequestReadyForReview → patch
   ├── c close/reopen ▶ y-or-n-p → closePullRequest / reopenPullRequest → patch
   └── k delete branch ▶ (merged or closed) y-or-n-p → deleteRef → patch
         patch: the PR's merge state from GitHub's answer · redraw
#+end_example

GitHub's API merges a closed pull request, so Approve refuses it first.
The merge is of the head the store holds: when the branch moved, GitHub
refuses ("Head branch was modified. Review and try the merge again."), and
=g= shows what changed.  Updating a branch that is up to date gets
GitHub's "There are no new commits on the base branch."

* F14 Re-review after new commits
GitHub knows which commit the viewer last reviewed (=viewerLatestReview=), and
it sets new changes on viewed files to =DISMISSED=.

#+begin_example
 load (F02)
   │
   ├─ comments others published after viewerLatestReview.submittedAt (D44):
   │    "new" after the byline, ┃ beside them; the headings count them
   │    [user] j n / j N ──▶ the next / previous one, what hides it unfolded
   ▼
 ◇ viewerLatestReview.commit ≠ headRefOid? ◇──no──▶ nothing extra
   │ yes
   ▼
 Commits heading: "2 new since your review"; new commits marked ┃
 header line: "2 new commits since your review — V l to see only them"
   │
 [user] V l   (or V c one commit, V r a range, V a all)
   │
   ▼
 ┌────────────────────────────────────────────────────────┐
 │ REST compare base…head (e.g. lastReviewed…headRefOid)  │
 │ store patches under :range; redraw Diff section from   │
 │ them; threads still come from the PR                   │
 └───────────────────────────┬────────────────────────────┘
                             ▼
 Diff heading: "Diff · since your last review (2 commits) · V a all changes"
                             │
 [user] c on a line in this view
                             │
                             ▼
 ◇ new-side line and inside the PR's own diff? ◇──no──▶ user-error
   │ yes                                                "Comment from the full diff:
   ▼                                                     this line isn't in the PR's diff"
 ⇢ F05 with the PR-diff line number (same file at head ⇒ same number)
#+end_example

"Since your last review" works only if the reviewed commit still exists in
history.  After a force push, compare may fail: say so and fall back to all
changes.

The marks of what is new since your review are Phase 6's ([[file:decisions.org::*D44 What is new since your last review: other people's comments, after it][D44]]): the
commits after the review's commit, and the comments and reviews others
published after it was submitted (a comment in a thread by =publishedAt=,
