#+title: UI — mockups, keys, faces, icons

Mockups show layout and intent.  Glyphs like ✓ ✗ ● ◐ 💬 stand in for
nerd-icons; each one is a semantic icon ([[*Icons][Icons]]) with a Unicode fallback.
Colours are described, not shown: every face inherits from Magit or built-in
faces ([[file:decisions.org::*D16 Own faces and one icon abstraction][D16]]).  =▾= and =▸= are magit-section's expanded/collapsed markers.

Design rules for every buffer:
- Read top-down like GitHub: what it is, its state, what needs me, then details.
- The first screen answers "what do I need to do here?": review state,
  pending comments, unviewed files, unresolved threads.
- Dim what is done (viewed files, resolved threads, outdated comments); keep
  what needs attention at normal weight.
- Every actionable thing shows its key the first time it appears, as a dim
  hint (=r reply · R resolve=).  A hint names the key that runs its command
  in that buffer, looked up when it is drawn, so it follows the user's own
  bindings and evil's (=i edit=, =D delete=); a command no key runs has no
  hint, and the read-only Phase 1 shows few.  =approve-show-hints= turns
  hints off, except the keys of an input buffer's header line and how to
  retry a failed load.
- No line exceeds =fill-column= + the indent; long text is wrapped (=shr=
  fills to =approve-fill-column=, default 80).
- People are written =@login=, as GitHub writes mentions ([[file:decisions.org::*D33 People are written as @login][D33]]); their names
  are in eldoc.  A commit's author whose e-mail GitHub links to no account
  is the name Git wrote, without an =@=.

* PR buffer — single layout (default)
Buffer name: =*approve: fuzzycode/approve#1234*=.  The header line is in
[[*Header line][Header line]].

Notes:
- The header line: number and title (=approve-title=, larger with
  =approve-title-height=, cut with … when long), then state badges on the
  right: Open/Closed/Merged and Draft, coloured by face.
- The buffer starts with the metadata rows (=approve-metadata-rows=, in order
  and which):
  Author, Repository (=o= opens it), Branch (head → base; =RET= copies a
  branch, =o= opens it; the Commits heading counts the commits), Opened
  (when it was opened and updated, and merged and by whom, or closed), then
  Reviewers … Status.
- Metadata rows are one section each (=approve-meta-*=), so each has its own
  keys (=l= on Labels edits labels) and eldoc (label descriptions, user names).
- Reviewer marks: ✓ approved, ✗ changes requested, 💬 commented, ○ requested
  but not reviewed yet.
- "Your pending review" appears only when one exists.  It lists the pending
  comments, and its heading counts them, replies included; =RET= jumps to
  one in the diff.
- An empty description shows a dim "No description provided."
- An edited description says so right after its heading:
  "Description · edited" (eldoc shows when).

Notes:
- The file list gives each file's size: its counts and a diffstat bar
  scaled to the largest file (=approve-diffstat-width=), and its threads on
  the whole file (the diff's "On this file"); its heading sums the
  unresolved ones.  =RET= jumps to the file's diff (single layout) or opens
  the diff buffer there (split layout).
- Diff file headings say which files are viewed, the file list doesn't:
  ✓ viewed (dim), · not viewed, ↻ viewed but changed since (GitHub's
  =DISMISSED=, highlighted); =v= toggles it, and the Diff heading counts
  the viewed files.  Then an icon of the change (the =file-*= icons: added,
  modified, deleted, renamed, copied, mode changed), in the =approve-file-*=
  faces; eldoc says it in words.  Then the path; the size is in the file
  list.  At the right edge, the threads on its lines, outdated ones too
  (unresolved, or all of them dim when all are resolved), lined up; the
  Diff heading sums the unresolved ones.  A moved file is written as git's
  diffstat writes it, =internal/engine/{queue.go → scheduler.go}=; a path
  too long for its room loses whole directories in the middle,
  =internal/…/page.tmpl=, as in the file list.  All files start collapsed;
  a file's body is drawn when it is first expanded.
- Line numbers (old, new) and the =+=/=-= marker are text that copying
  leaves out ([[file:decisions.org::*D28 Diff line numbers are text that copying leaves out][D28]]); =approve-diff-line-numbers= hides the numbers.  Added
  lines use =magit-diff-added=, removed =magit-diff-removed=, context
  =magit-diff-context=; changed words in pairs of removed and added lines
  are marked when =approve-diff-refine-hunk= is non-nil (the default).
  Code is coloured by the file's major mode over those backgrounds
  (=approve-diff-fontify=, [[file:decisions.org::*D30 Diff hunks are syntax-highlighted by default][D30]]).
- Threads sit right under the line they belong to (the last line of a
  range).  For a multi-line thread the covered lines get a thin bar in the
  fringe while point is on the thread.
- A thread is a box open on the right, on purpose: code blocks, tables and
  URLs that are not wrapped, lines that wrap in a narrow window and images
  would each put a right border in another column.  Closing it (padding to
  the box width, a =│= copying leaves out) can come later for text lines.
- A line with threads has a speech bubble and their count at the right
  edge (unresolved ones; all of them, dim, when all are resolved).  It
  takes the line's background but not its colour, so a bubble on a
  removed line looks like any other.  The line folds its threads: =TAB=
  on it, or anywhere in them, folds them away, and only the bubble is
  left.  Threads don't fold one by one.
  The bubble isn't text (it is drawn before the line's end), so moving
  up and down never puts point in it, and copying leaves it out.
  Lines whose threads are all resolved start folded; so does "On this
  file" when its threads are.  Outdated threads (line gone from the diff)
  are collected under the file: "▸ Outdated (2)".  =T= folds every thread in
  the diff, or unfolds them all, and files expanded later follow ([[*Keys][Keys]]).
- Thread marks (💬 N: the bubbles, the counts of the file headings and of
  the file list) are neutral, except one counting a thread that asks for
  changes: an unresolved thread started in a review that requested
  changes, while that review is its author's latest verdict.  That mark
  is red (=approve-thread-mark-changes-requested=), and turns neutral
  when the thread is resolved, the review dismissed, or its author
  approves later ([[file:decisions.org::*D34 A thread mark is red only while it asks for changes][D34]]).
- A pending comment says "✎ Pending" (=approve-pending=) where a published
  one says when it was written, so the two can't be mistaken.  Only that
  label is coloured: the comment has no background.

* Header line
Shown in the PR buffer and the diff buffer; it stays visible while scrolling.
It names the PR; counts are in the sections (viewed files and unresolved
threads on lines on Diff, unresolved threads on whole files on Files
changed, pending comments on Your pending review, checks on Status and
Checks).

#+begin_example
 #1234 Add retry logic to the GraphQL client                       ● Open  ◌ Draft
 #1234 Add retry logic to the GraphQL client · ⟳ updated on GitHub — g to refresh  ● Open
 #1234 · loading pull request, files, threads…
#+end_example

The second form appears when change detection ([[file:decisions.org::*D23 Remote changes are announced, never auto-applied][D23]]) finds new commits or
comments (=approve-pr-header-line-functions=).  The third is the first moment,
before the title has loaded.

When the pull request itself can't load (its core query fails), or GitHub
gets no token (any query), there is nothing worth showing: the buffer shows
that one error instead of each section repeating it, and the echo area says
it.  A token error replaces another, as it is the cause.

access to it." for a 404, and "Could not load the pull request." for any
other failure of the core query (a timeout, a 502).

* Comment input buffer
Opened below the PR buffer.  The target lines stay highlighted in the PR
buffer until the input is committed or aborted.

#+begin_example
 ┌──────────────────────────────────────────────────────────────────────────────┐
 │ *approve: fuzzycode/approve#1234*                                            │
 │        41      -          (timeout approve-api-timeout))                     │
 │            41  +          (timeout approve-api-timeout)            ░░ target │
 │            42  +          (retries approve-api-retries))           ░░ target │
 │        42  43        (when progress-message                                  │
 ├──────────────────────────────────────────────────────────────────────────────┤
 │ Comment on approve-api.el:41–42 · pending review    C-c C-c send · C-c C-k ✗ │ header
 │ Should `retries` be part of the defgroup?                                    │
 │                                                                              │
 │ ```suggestion                                                                │
 │          (timeout approve-api-timeout)                                       │
 │          (retries (or retries approve-api-retries)))                         │
 │ ```                                                                          │
 │ -:**- *approve-input: comment approve-api.el:41-42*   Approve-Input  C-c C-s │
 └──────────────────────────────────────────────────────────────────────────────┘
#+end_example

| Key       | Does                                                           |
|-----------+----------------------------------------------------------------|
| =C-c C-c= | Send (commit)                                                  |
| =C-c C-k= | Abort; the text is kept as a draft for this target             |
| =C-c C-s= | Insert a suggestion block prefilled with the target lines      |
| =C-c C-p= | Preview rendered markdown (GitHub renders it) in a side window |
| =C-c @=   | Insert a mention (completing-read over the people, PR's first) |
| =M-TAB=   | Complete =@user=, =#123=, =:emoji:= at point                   |

The header-line text names the action: "Comment on…", "Reply to @bob on…",
"Edit comment", "Edit description", "Review body — Approve", "New title"
(single line).  Its right end names the keys: send and abort, then suggest
while the text is on code and has no suggestion yet, else preview (not for
a single line).  They are the keys bound in the input buffer, shown even
when =approve-show-hints= is nil.  Evil users start in insert state.

** Submit review (=S=)
#+begin_example
 Submit review  #1234                              pending: 2 comments · 1 reply
 Verdict                        Body
  a Approve                      e Edit body…     "Thanks! Two nits inline."
  r Request changes
  c Comment
 Other
  X Discard pending review       q Quit
#+end_example

Choosing a verdict opens the body input (prefilled with the draft body, else
the pending review's).  =C-c C-c= submits it.  =C-u a= approves with no body
and no input buffer.  With no pending review, =a=/=r=/=c= create and submit a
review in one call.  Request changes and Comment need a body when there are
no comments; on your own pull request, Approve and Request changes are dimmed,
as GitHub refuses them ([[file:decisions.org::*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]).

- The buffer uses the file's major mode (font-lock, imenu, which-function).
- Fringe: =▌= added or changed lines, =▸= where lines were removed.

* Eldoc
Extended information about the thing at point comes in two tiers, from one
eldoc function ([[file:decisions.org::*D27 Extended information through eldoc: one line, then the eldoc buffer][D27]]):

- Echo area :: automatic when point rests on something; one line built from
  data already loaded, so it appears at once.
- Eldoc buffer :: on demand with =K= (=eldoc-doc-buffer=); everything worth
  knowing.  Details that aren't loaded yet are fetched then, shown as
  "⟳ loading details…" until they arrive, and cached for the session.  Users
  who want it always visible set =eldoc-echo-area-prefer-doc-buffer=, or use
  eldoc-box and similar frontends.

* Keys
Keys are a draft to check in Phases 1–2.  Principles:
- Emacs: single letters as in Magit; the same letter in every Approve buffer
  means the same thing.
- Evil normal state: never shadow motions (h j k l w b e W B E 0 ^ $ gg G
  f t % { } H M L), search (/ n N), visual (v V C-v) or yank (y).  =j=, =k=
  and the arrow keys are evil's screen-line motions (=evil-next-visual-line=),
  as Magit's own line motions are (=line-move-visual=): by logical line,
  moving down from a collapsed heading stops in its hidden body and Magit
  puts point back at the heading's end.  Visual
  line selection (=V=) picks a range to comment on.  =?= opens dispatch, as in
  evil-collection's Magit.
- Every command is also in the dispatch transient, so a missing key is never
  a missing feature.

| Command                       | Emacs         | Evil normal           | Context                   |
|-------------------------------+---------------+-----------------------+---------------------------|
| Dispatch                      | =?=           | =?=                   | any                       |
| Refresh (=C-u=: clear caches) | =g=           | =gr=                  | any                       |
| Bury / back                   | =q=           | =q=                   | any                       |
| Toggle section                | =TAB=         | =TAB= =za=            | section                   |
| Fold / unfold every thread    | =T=           | =zM= =zm= / =zR= =zr= | any                       |
| Next / previous section       | =n= =p=       | =gj= =gk= =C-j= =C-k= | any                       |

Toggling a section (=approve-section-toggle=, also what =RET= does where there
is nothing to visit) folds the section at point, except inside the diff: on a
diff line with threads it folds the threads, and in a thread it folds the
threads of its line (or its group, "On this file" or "Outdated"); on a
line without threads it folds the hunk.

=T= (=approve-toggle-threads=) folds every thread in the diff down to its
line's bubble, "On this file" and "Outdated" included, or unfolds them all
when they are folded, resolved and outdated ones too.  The choice holds for
files expanded later and across =g=, until it is turned again; =TAB= still
folds one line.  Evil users fold all with =zM= (or =zm=) and unfold all with
=zR= (or =zr=), as in vim.

Input buffers: =C-c C-c= send, =C-c C-k= abort, =C-c C-s= suggestion, =C-c C-p=
preview, =C-c @= mention (same in every state).

In evil's visual state, =c=, =s=, =r= and =C= act on the selection: =V= picks
lines of the diff to comment on or suggest a change of, and selected text is
quoted by a reply or a conversation comment.  A command that doesn't apply to
the thing at point applies to the section around it: on a comment's =@author=,
=r= replies to the comment and =e= edits it.  A range is named as GitHub does:
=a.go:13–14=, or =a.go:-13–+14= from a removed line to an added one.
