#+title: UI — mockups, keys, faces, icons

Mockups show layout and intent.  Glyphs like ✓ ✗ ● ◐ 💬 stand in for
nerd-icons; each one is a semantic icon ([[*Icons][Icons]]) with a Unicode fallback.
Colours are described, not shown: every face inherits from Magit or built-in
faces ([[file:decisions.org::*D16 Own faces and one icon abstraction][D16]]).  =▾= and =▸= are magit-section's expanded/collapsed markers.

Design rules for every buffer:
- Read top-down like GitHub: what it is, its state, what needs me, then details.
- The first screen answers "what do I need to do here?": review state,
  pending comments, unviewed files, unresolved threads.
- Dim what is done (viewed files, resolved threads, outdated comments); keep
  what needs attention at normal weight.
- Every actionable thing shows its key the first time it appears, as a dim
  hint (=r reply · R resolve=).  A hint names the key that runs its command
  in that buffer, looked up when it is drawn, so it follows the user's own
  bindings and evil's (=i edit=, =D delete=); a command no key runs has no
  hint, and the read-only Phase 1 shows few.  =approve-show-hints= turns
  hints off, except the keys of an input buffer's header line and how to
  retry a failed load.
- No line exceeds =fill-column= + the indent; long text is wrapped (=shr=
  fills to =approve-fill-column=, default 80).
- What sits on the right of a line (counts and states on headings, key
  hints, the diff's file statistics, the header line's state) ends at
  =approve-page-width=, default 110: right of the filled text and the
  indentation of threads.  Narrow frames or side-by-side windows can set it
  lower, such as 88.  Mockups show intent, so theirs is closer to 80.
- People are written =@login=, as GitHub writes mentions ([[file:decisions.org::*D33 People are written as @login][D33]]); their names
  are in eldoc.  A commit's author whose e-mail GitHub links to no account
  is the name Git wrote, without an =@=.

* PR buffer — single layout (default)
Buffer name: =*approve: fuzzycode/approve#1234*=.  The header line is in
[[*Header line][Header line]].

Notes:
- The header line: number and title (=approve-title=, larger with
  =approve-title-height=, cut with … when long), then state badges on the
  right: Open/Closed/Merged and Draft, coloured by face.
- The buffer starts with the metadata rows (=approve-metadata-rows=, in order
  and which):
  Author, Repository (=o= opens it), Branch (head → base; =RET= copies a
  branch, =o= opens it; the Commits heading counts the commits), Opened
  (when it was opened and updated, and merged and by whom, or closed), then
  Reviewers … Status.
- Metadata rows are one section each (=approve-meta-*=), so each has its own
  keys and eldoc (label descriptions, user names): =RET= on Labels,
  Assignees, Reviewers or Milestone changes it, as =l a A M= do anywhere,
  and =o= opens the label, person or milestone at point.
- Reviewer marks: ✓ approved, ✗ changes requested, 💬 commented, ○ requested
  but not reviewed yet.
- "Your pending review" appears only when one exists.  It lists the pending
  comments, and its heading counts them, replies included; =RET= jumps to
  one in the diff.
- An empty description shows a dim "No description provided."
- An edited description says so right after its heading:
  "Description · edited" (eldoc shows when).

Notes:
- The timeline shows conversation comments, reviews (with their body and a
  count of code comments; =RET= jumps to them), pushes, label/assignee/title
  changes, force pushes, ready-for-review, merges and closes.
  =approve-timeline-event-types= picks which.
- Events by bots, and runs of small events, can be folded into one line
  ("github-actions added 3 labels").
- Minimized (hidden) comments show as one dim line with the reason.  =H=
  hides a comment or a review, asking for the reason, or shows it again.
- =RET= on a commit, in the commits or a push, shows it in Magit's revision
  buffer from a local clone that has it (=approve-clone-directories=,
  [[file:decisions.org::*D37 Clones are found where Magit lists them; a commit opens in Magit][D37]]), else on GitHub.
- What came after your last review (=viewerLatestReview=) is new
  ([[file:decisions.org::*D44 What is new since your last review: other people's comments, after it][D44]]): the commits after its commit, marked =┃= and "new", and
  the comments and reviews others published after it, which say "new"
  after their byline, the timeline's line heavy (=┃=) beside them, all in
  =approve-new=.  The headings count them.  Your own and pending ones never
  are; before your first review nothing is.  =j n= and =j N= go to the
  next and previous new comment, here or in the diff's threads.

Notes:
- The file list gives each file's size: its counts and a diffstat bar
  scaled to the largest file (=approve-diffstat-width=), and its threads on
  the whole file (the diff's "On this file"); its heading sums the
  unresolved ones.  =RET= on a file opens it whole ([[*File view][File view]]), as on its
  heading in the diff; =j /= and =]u= jump to a file's diff.
- Diff file headings say which files are viewed, the file list doesn't:
  ✓ viewed (dim), · not viewed, ↻ viewed but changed since (GitHub's
  =DISMISSED=, highlighted); =v= toggles it, and the Diff heading counts
  the viewed files.  Then an icon of the change (the =file-*= icons: added,
  modified, deleted, renamed, copied, mode changed), in the =approve-file-*=
  faces; eldoc says it in words.  Then the path; the size is in the file
  list.  At the right edge, the threads on its lines, outdated ones too
  (unresolved, or all of them dim when all are resolved), lined up; the
  Diff heading sums the unresolved ones.  A moved file is written as git's
  diffstat writes it, =internal/engine/{queue.go → scheduler.go}=; a path
  too long for its room loses whole directories in the middle,
  =internal/…/page.tmpl=, as in the file list.  All files start collapsed;
  a file's body is drawn when it is first expanded.
- Line numbers (old, new) and the =+=/=-= marker are text that copying
  leaves out ([[file:decisions.org::*D28 Diff line numbers are text that copying leaves out][D28]]); =approve-diff-line-numbers= hides the numbers.  Added
  lines use =magit-diff-added=, removed =magit-diff-removed=, context
  =magit-diff-context=; changed words in pairs of removed and added lines
  are marked when =approve-diff-refine-hunk= is non-nil (the default).
  Code is coloured by the file's major mode over those backgrounds
  (=approve-diff-fontify=, [[file:decisions.org::*D30 Diff hunks are syntax-highlighted by default][D30]]).
- Threads sit right under the line they belong to (the last line of a
  range).  For a multi-line thread the covered lines get a thin bar in the
  fringe while point is on the thread.
- A thread is a box open on the right, on purpose: code blocks, tables and
  URLs that are not wrapped, lines that wrap in a narrow window and images
  would each put a right border in another column.  Closing it (padding to
  the box width, a =│= copying leaves out) can come later for text lines.
- A line with threads has a speech bubble and their count at the right
  edge (unresolved ones; all of them, dim, when all are resolved).  It
  takes the line's background but not its colour, so a bubble on a
  removed line looks like any other.  The line folds its threads: =TAB=
  on it, or anywhere in them, folds them away, and only the bubble is
  left.  Threads don't fold one by one.
  The bubble isn't text (it is drawn before the line's end), so moving
  up and down never puts point in it, and copying leaves it out.
  Lines whose threads are all resolved start folded; so does "On this
  file" when its threads are.  Outdated threads (line gone from the diff)
  are collected under the file: "▸ Outdated (2)".  =T= folds every thread in
  the diff, or unfolds them all, and files expanded later follow ([[*Keys][Keys]]).
- Thread marks (💬 N: the bubbles, the counts of the file headings and of
  the file list) are neutral, except one counting a thread that asks for
  changes: an unresolved thread started in a review that requested
  changes, while that review is its author's latest verdict.  That mark
  is red (=approve-thread-mark-changes-requested=), and turns neutral
  when the thread is resolved, the review dismissed, or its author
  approves later ([[file:decisions.org::*D34 A thread mark is red only while it asks for changes][D34]]).
- A pending comment says "✎ Pending" (=approve-pending=) where a published
  one says when it was written, so the two can't be mistaken.  Only that
  label is coloured: the comment has no background.
- A comment someone else published after your last review says "new"
  after its byline, and its bar is heavy, =┃=, both in =approve-new= ([[file:decisions.org::*D44 What is new since your last review: other people's comments, after it][D44]]).
  A file's heading counts its new comments before its threads, and the
  Diff heading sums them.  =j n= and =j N= go to the next and previous one,
  expanding the file and unfolding the line they are under.

A suggested change that can be committed names the keys after its title
([[file:flows.org::*F23 Commit a suggestion, or a batch of them][F23]], [[file:decisions.org::*D41 Suggestions are committed the way GitHub's button does (SP7)][D41]]): =x= commits it, =b= adds it to the batch (=a= and =A=
in evil).  With a batch, the others say "b add to batch" alone, as =x=
then commits the batch.  One in the batch says "✓ in the batch"
(=approve-suggestion-batched=), even when =approve-show-hints= is nil.  A
suggestion that can't be committed (pending, outdated, on removed lines,
in a closed pull request) says nothing; =K= and the dispatch say why.
These are overlays on the box GitHub's HTML draws, put back after each
redraw.

* Header line
Shown in the PR buffer and the diff buffer; it stays visible while scrolling.
It names the PR; counts are in the sections (viewed files and unresolved
threads on lines on Diff, unresolved threads on whole files on Files
changed, pending comments on Your pending review, checks on Status and
Checks).

#+begin_example
 #1234 Add retry logic to the GraphQL client                       ● Open  ◌ Draft
 #1234 Add retry logic … · ⟳ updated on GitHub — g to refresh · 2 new commits  ● Open
 #1234 · loading pull request, files, threads…
 #1234 Add retry logic … · 2 suggestions in the batch · x commits them  ● Open
#+end_example

The second form appears when change detection ([[file:decisions.org::*D23 Remote changes are announced, never auto-applied][D23]]) finds that the PR
changed on GitHub (=approve-pr-header-line-functions=).  After "to
refresh" it says what is new, as far as the check tells: "2 new commits"
("the branch changed" after a force push), "1 new comment", "3 new
reviews"; an edit alone (the title, the description, a comment) adds
nothing.  It is in =approve-updated=, the key in =approve-hint-key=, and it
names the key bound to =approve-pr-refresh=.  It stays until =g=, which
drops it as the load starts.  The third is the first moment, before the
title has loaded.  The fourth counts the suggestions waiting in the batch
([[file:flows.org::*F23 Commit a suggestion, or a batch of them][F23]]), in =approve-suggestion-batched=.

(title, search filter or function, limit, collapsed at first), as in
approve-v2, and "Recently opened" lists the pull requests opened in this
Emacs session ([[file:decisions.org::*D39 The dashboard: lists loaded anew each time, "Recently opened" for the session][D39]]).

The rows are =approve-list.el='s, shared with the search ([[file:decisions.org::*D38 Lists of pull requests: a state icon first, columns the user picks, GitHub's review decision][D38]]).
Columns: state (● open, ◌ draft, ⮌ merged, ⊘ closed), number, title (a
draft's dim), repository, author, updated (=5m 2h 3d 2w 4mo 1y=), checks of
the last commit (✓ ✗ ◐ ·), GitHub's review decision (✓ approved, ✗
changes requested, ○ review required, · none).  =approve-list-columns=
says which columns, in what order and how wide; the title takes what's
left up to =approve-page-width=.  Whether an unread mark joins them waits
for notifications ([[file:decisions.org::*Open questions][Q6]]).

The title line names the viewer and when the lists were loaded.
=M-x approve-dashboard= loads every list again each time it shows the
buffer, as =g= does; =G= (=gR= in evil, as =G= is a motion there) loads
the list at point alone.  A list keeps its rows while it loads again, with
"⟳ loading…" on its heading; before its first answer it says "⟳
Loading…", and a failed one says why, with how to retry.  A token error
is shown once, for the whole dashboard.  A heading counts what GitHub
finds; when a list shows fewer, its last line says how many more:

#+begin_example
 ▾ Needs my review (23)

   …
   … 3 more · o show them on GitHub
#+end_example

On a row, =RET= opens the PR, =o= opens it in the browser, =y= copies its
URL, =K= shows its details (eldoc), and =TAB= folds its list.  On a list's
heading, =o= opens its search on GitHub and =y= copies the search.  =T=
folds every list, or unfolds them all when they are folded, and =O= every
list but the one at point; a folded list stays folded when the dashboard
loads again.  Evil folds as in vim: =za=, =zo= and =zc= the list at point
(from its rows too), =zM= (or =zm=) every list, =zR= (or =zr=) unfolds
them all, and =zp= folds the others.  =?= opens the dashboard's dispatch:

* Mode-line count (Phase 8)
=approve-mode-line-mode= (a global minor mode, off by default) puts a count
of pull requests in the mode line: an icon and a number for each list of
=approve-dashboard-sections= marked =:mode-line t=, "Needs my review" by
default ([[file:decisions.org::*D48 A count in the mode line, from the dashboard's lists][D48]]).  It asks GitHub every =approve-mode-line-interval=
seconds (300), when Emacs gets the focus back, and after a review is
submitted.
#+begin_example
 <N>  approve-api.el   42%  L41  (ELisp/l)                                  PR 3
#+end_example

The icon is the list's =:icon=, =pull-requests= when it has none
(=nf-md-source_pull=; the fallback "PR" is shown here).  Another marked
list adds its own, in the lists' order: =PR 3  ✗ 1=.  The number is GitHub's
count; at 0 the icon and the 0 stay, dim, so it is seen to run.  Before
the first answer it shows =PR …=; when GitHub can't be asked, the last
count stays (or =PR ?=) and the tooltip says why.

Its tooltip, and its clicks:

** Merge / state (=m=)
#+begin_example

The title line is GitHub's merge box in one line ([[file:decisions.org::*D42 Merging as GitHub's merge box does, checked first (F13)][D42]]): conflicts,
checks, reviews, "behind main" when the base's rules want it up to date,
auto-merge and the merge queue; blocked, it reads "✗ conflicts · ✗ 1
check failing · ✗ 1 change requested".  Merged, it says who merged it
(and that the branch is deleted); closed, that it is closed.  Only the
methods the repository allows are apt, and each command is dimmed where
it would refuse, saying why when run: a draft, conflicts, GitHub still
working it out, the base's rules (unless the viewer may bypass them), a
merge queue.

=m= and =s= open the commit message in an input buffer, starting from
GitHub's (its first line is the title, the rest the body); =C-c C-c=
merges.  =C-u m=, =C-u s= and =r= ask =y-or-n-p= and use GitHub's message.

repository does)" where the repository deletes merged branches itself.

the message.  =u= merges the base into the branch, =U= rebases it; the
pull request loads again once GitHub has the new commits.  =k= deletes
the branch of a merged or closed pull request.  =D=, =c= and =Q= say
what they will do ("Mark ready for review", "Reopen pull request",
"Remove from merge queue").

** Metadata pickers
Labels, assignees and reviewers use =completing-read-multiple=, the milestone
=completing-read=.  The current values are in the input already, separated by
commas: removing one takes it away.  Candidates are annotated, ✓ on the ones
the pull request has:

#+begin_example
 Labels: enhancement,api,█
   api              ✓ ▇▇▇▇ Talking to GitHub
   bug                ▇▇▇▇ Something isn't working
   documentation      ▇▇▇▇ Improvements or additions to documentation
   enhancement      ✓ ▇▇▇▇ New feature or request
#+end_example

- Labels (=l=): the repository's, by name, with their colour and
  description.
- Assignees (=a=): the people who can be assigned, with their names.
- Reviewers (=A=): GitHub's suggestions first (and why: "suggested,
  commented"), then who is asked now, then the people who can be assigned
  and the teams of the organization that owns the repository, each with
  their latest verdict.  The pull request's author is never offered: GitHub
  drops them from the requests without a word.
- Milestone (=M=): "No milestone" when there is one, then the open
  milestones, those due first first and those with no due date last, with
  their due date and progress.  =RET= alone keeps the current one.

The lists come from the repository's metadata (D24), fetched the first time
and waited for, the echo area saying so.  Choosing what the pull request has
sends nothing ("no change to the labels"); else only the difference goes:
the labels added, then those removed.

* File view
=RET= on a diff line opens the whole file at that line: at the PR head, or
at its base for a removed line.  =RET= on a file, its heading in the diff

  and the comment is the same as one written in the diff; on other lines

* Eldoc
Extended information about the thing at point comes in two tiers, from one
eldoc function ([[file:decisions.org::*D27 Extended information through eldoc: one line, then the eldoc buffer][D27]]):

- Echo area :: automatic when point rests on something; one line built from
  data already loaded, so it appears at once.
- Eldoc buffer :: on demand with =K= (=eldoc-doc-buffer=); everything worth
  knowing.  Details that aren't loaded yet are fetched then, shown as
  "⟳ loading details…" until they arrive, and cached for the session.  Users
  who want it always visible set =eldoc-echo-area-prefer-doc-buffer=, or use
  eldoc-box and similar frontends.

** Echo area

 #1234 Add retry logic to the GraphQL client — @alice (member) · changes requested · checks running · 5 comments, 15 threads · +340 −56 in 12 files · feature/retry → main
#+end_example

The echo line shows only what is already loaded ([[file:decisions.org::*D29 Echo lines show what the store holds; names and emails wait for K][D29]]): a person's public
email, a team's name and members, and who reacted come with =K=.  Details
that =K= fetched before stay cached and show in the echo line too.

* Keys
Keys are a draft to check in Phases 1–2.  Principles:
- Emacs: single letters as in Magit; the same letter in every Approve buffer
  means the same thing.
- Evil normal state: never shadow motions (h j k l w b e W B E 0 ^ $ gg G
  f t % { } H M L), search (/ n N), visual (v V C-v) or yank (y).  =j=, =k=
  and the arrow keys are evil's screen-line motions (=evil-next-visual-line=),
  as Magit's own line motions are (=line-move-visual=): by logical line,
  moving down from a collapsed heading stops in its hidden body and Magit
  puts point back at the heading's end.  Visual
  line selection (=V=) picks a range to comment on.  =?= opens dispatch, as in
  evil-collection's Magit.
- Every command is also in the dispatch transient, so a missing key is never
  a missing feature.

Toggling a section (=approve-section-toggle=, also what =RET= does where there
is nothing to visit) folds the section at point, except inside the diff: on a
diff line with threads it folds the threads, and in a thread it folds the
threads of its line (or its group, "On this file" or "Outdated"); on a
line without threads it folds the hunk.  =RET= on a diff line opens the
whole file there ([[*File view][File view]]), where =TAB= folds a line's threads and
=RET= comes back to the line in the diff.

=T= (=approve-toggle-threads=) folds every thread in the diff down to its
line's bubble, "On this file" and "Outdated" included, or unfolds them all
when they are folded, resolved and outdated ones too.  The choice holds for
files expanded later and across =g=, until it is turned again; =TAB= still
folds one line.  Evil users fold all with =zM= (or =zm=) and unfold all with
=zR= (or =zr=), as in vim; =zo= and =zc= unfold and fold what =TAB=
toggles.  In the dashboard, the same keys fold its lists.

=O= (=approve-fold-others=, =zp= in evil) folds every section but the one
at point, which unfolds:
the top-level sections (pending review, description, checks, commits,
conversation, files, diff), and in the diff every file but the one at
point.  In the dashboard it folds every list but the one at point.

Input buffers: =C-c C-c= send, =C-c C-k= abort, =C-c C-s= suggestion, =C-c C-p=
preview, =C-c @= mention (same in every state).  A one-line input (a title)
sends with =RET= too.  In Approve's minibuffer prompts (the pickers, reasons,
reactions, a file, a URL), =C-c C-c= does what =RET= does: it is the key that
applies and sends everywhere ([[file:decisions.org::*D40 C-c C-c applies and sends, everywhere][D40]]).

In evil's visual state, =c=, =s=, =r= and =C= act on the selection: =V= picks
lines of the diff to comment on or suggest a change of, and selected text is
quoted by a reply or a conversation comment.  =?= opens the dispatch there
too, and the command picked in it acts on the selection.  A command that doesn't apply to
the thing at point applies to the section around it: on a comment's =@author=,
=r= replies to the comment and =e= edits it.  A range is named as GitHub does:
=a.go:13–14=, or =a.go:-13–+14= from a removed line to an added one.

In a file's buffer of a clone, the feedback mode's commands are in
=approve-feedback-command-map=, under =approve-feedback-prefix-key=: =C-c '=
by default, in Emacs and in evil's states ([[file:decisions.org::*D50 The feedback mode: a prefix key, evil's fold keys, and a bubble in the mode line][D50]]).  Set it to another key,
or nil, and bind the map elsewhere too, under a leader key for example:
#+begin_src emacs-lisp
(setopt approve-feedback-prefix-key "C-c a")   ; another prefix, or nil
(evil-define-minor-mode-key 'normal 'approve-feedback-mode
  (kbd "SPC m") approve-feedback-command-map)  ; under an evil leader too
#+end_src

minor modes.  A line's threads are its innermost fold ([[file:decisions.org::*D51 Threads fold inside the buffer's own folds][D51]]):
