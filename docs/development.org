#+title: Development

How we write, build and test Approve.  Most code is written by AI agents and
read by humans ([[file:project.org][project.org]]), so the code must be plain, local and
predictable.

* Working as an agent
1. Read [[file:index.org][index.org]], then the docs the task links (decision, flow, mockup).
2. Check the code: the truth is in the code, not in an earlier conversation.
   Use absolute paths.
3. If the docs don't answer a question, ask.  Don't guess a design decision;
   propose one and record it in [[file:decisions.org][decisions.org]] once agreed.
4. Do one task in small steps, one commit each.  Compile and test after every
   change.
5. Tick the task in [[file:roadmap.org][roadmap.org]], and update any doc the change affects, in
   the same commit.
6. Reload Approve in the author's running Emacs after each unit of work, so
   it can be tried at once: =make build=, then load =dev/load.el= there
   (=(load-file "~/workspace/approve/dev/load.el")= through the Emacs
   tools) and check =*Messages*=.  Nothing important is lost by a reload.
7. Never let a command wait without a limit: an agent can't press =C-g=.
   Run every build, test, lint, Emacs and network command under
   =timeout= (=timeout 600 make test=, =timeout 60 emacs --batch …=,
   =timeout 60 gh api …=), give the tool its own timeout too, and send
   long output to a file to read the end of (=> /tmp/test.log 2>&1=).  A
   test file that doesn't load, an Emacs waiting for input (a passphrase,
   a =y-or-n-p=) or a request that never answers then fails in time
   instead of hanging the session.  Run one test file alone with
   =timeout 120 cask exec emacs -Q --batch -L lisp -L tests -L . -l buttercup -l tests/test-x.el -f buttercup-run=.

* Commands
| Command        | Does                                                         | Today                                      |
|----------------+--------------------------------------------------------------+--------------------------------------------|
| =make install= | =cask install=                                               | exists                                     |
| =make build=   | byte-compile =lisp/*.el=                                     | exists                                     |
| =make test=    | buttercup on =tests/=                                        | exists                                     |
| =make lint=    | byte-compile with warnings as errors, package-lint, checkdoc | exists                                     |
| =make cover=   | tests with undercover (text report)                          | exists                                     |
| =make clean=   | remove =.elc=                                                | exists                                     |
| =make docs=    | rebuild the flow diagrams and =docs/html/flows.html=         | exists (needs graphviz)                    |
| =make try=     | a fresh Emacs (=-Q=, Cask dependencies only) that replays    | exists; =M-x approve-dev-try= does the     |
|                | the fixtures and lists their PRs (=dev/try.el=)              | same in any Emacs with Approve loaded      |

To try Approve in the Emacs you work in, =M-x load-file= =dev/load.el=.  It
loads every module from =lisp/= (compiled after =make build=), takes the
dependencies that Emacs lacks from Cask, replays the fixture PRs and sends
other URLs to GitHub (=approve-dev-offline-fallback=).  Loading it again
reloads everything and redraws the open PR buffers.

The shell is fish: wrap loops in =bash -c '…'=.  Fish has no heredocs
(=<<EOF=): write the text to a file first (a commit message: =git commit
-F /tmp/msg.txt=).

* Emacs Lisp conventions
- =lexical-binding: t= in every file.  Full package headers; a Commentary that
  says what the module is for and what it must not do (its layer rules,
  [[file:architecture.org::*Layers][architecture]]).
- Names: public =approve-…=, private =approve--…=, per module
  =approve-<module>-…= where it helps.  Section inserters are
  =approve-insert-<name>-section=; section classes =approve-<name>-section=.
- Style: the [[https://github.com/bbatsov/emacs-lisp-style-guide][Emacs Lisp style guide]].  Small functions with docstrings;
  =cl-defun= with keyword arguments for anything with more than three
  parameters or optional callbacks.
- =magit-insert-heading= takes a child count as its first argument; use it.
- Libraries: =dash=, =seq=, =map=, =subr-x=, =cl-lib= are fine.  Prefer
  built-ins when they read as well.
- No =cl-letf= on other packages' functions, and no advice on them, in
  package code (lesson from approve-mvp/old).
- Errors: =user-error= for things the user can fix, explaining how; =define-error=
  types under =approve-error= for the rest.
- Evil: never =require= evil.  Bindings live in =approve-evil.el=, which an
  Approve mode requires when =(featurep 'evil)= (D17; package-lint rejects
  =with-eval-after-load=).  Never shadow evil's motions there.
- Faces only from =approve-faces.el=; icons only through =approve-icon=.
- A new command joins the dispatch transient (=?=), and any other menu it
  fits, in the commit that adds it; =tests/test-approve-menus.el= fails
  while a bound command can't be reached from =?=.  A command that
  changes the PR starts with its preflight, which changes nothing, and
  names it in its =approve-preflight= property, so the menu dims it where
  it would refuse ([[file:decisions.org::*D06 Menus are transients; everything is reachable from =?=][D06]]).
- Every =defcustom= has =:type=, =:group= and a docstring with an example.
- Async: callbacks never assume the buffer is alive or point unchanged.
  Capture what you need before the request.

* GraphQL conventions
- One fragment per type, named =<Type>Fields=, in
  =graphql/fragments/<type>.graphql=.  Include fragments with
  =${include:fragments/<type>.graphql}=; the loader dedupes.
- Every object with an =id= selects =__typename= (the store needs both and
  signals an error without them).
- Mutations return the changed object through its fragment, so the store
  patches it.
- Queries take variables named in camelCase as GitHub does
  (=$owner=, =$name=, =$number=, =$after=).
- Every query selects =rateLimit { cost remaining resetAt }=.
- Try new queries in a GraphQL client first; the =.graphql= files load
  unchanged except for the include lines.

* Tests
Buttercup.  Test behaviour, not implementation details: what the user sees
and what goes to GitHub.

| Layer     | How                                                                              |
|-----------+----------------------------------------------------------------------------------|
| graphql   | Loader on temp files: includes, dedupe, cycles, missing files                    |
| api       | Fake =approve-api-transport=, spy on =ghub-request=; timeouts, errors, queue     |
| model     | Load fixtures; selectors; patching; list edits; pagination                       |
| renderers | Render a fixture into a temp buffer; assert sections exist, contain text,        |
|           | carry the right context; no full-buffer string snapshots                         |
| context   | Put point on lines of a rendered fixture; assert the context plist               |
| actions   | Fake API: assert the mutation and variables sent, and the store afterwards       |
| input     | Commit/abort callbacks, drafts kept on abort                                     |

- Fixtures are recorded with =approve-dev-record= from real PRs, then scrubbed:
  no tokens, and personal data replaced where possible.  Their format is in
  [[file:../tests/fixtures/README.org][tests/fixtures/README.org]].  Until real recordings replace them, the
  fixtures are synthetic, built by =tests/fixtures/generate.el= in the same
  format.
- No test touches the network or the user's config (=emacs -Q= in batch).
- Development helpers (=approve-dev.el=) are not packaged.  The parts tests
  rely on (fixture files, replay, recording) have tests of their own.

* Commits and branches
- Conventional commits (=feat(diff): …=, =fix(api): …=, =docs: …=,
  =test: …=, =build: …=, =refactor: …=), as this repository's history does.
- One logical change per commit, with its tests and doc updates.
- Work on =feature/…= branches; =main= always builds and passes tests.

* Scratch repository
Writes are tried on =fuzzycode/test-approve= (private), never on another
repository: commands under development, spikes, recording fixtures.
- Its pull requests are set up for trying Approve; #4 holds the author's
  pending review.  #8 holds the SP1 experiments ([[file:decisions.org::*D32 Reviews are written the way GitHub's API allows (SP1)][D32]]): threads across
  hunks, from a removed line to an added one, on a context line by its old
  number, and on a whole file.
- #9 is by github-actions[bot], for what one can't do on one's own pull
  request (approve, request changes).  The "Bot pull request" workflow
  (=bot-pr.yml=, run by hand) opens another; =bot.yml= leaves a bot comment.
- Operations can be tried there by hand with =gh api graphql=
  ([[file:../graphql/README.org][graphql/README.org]]).
- =dev/scratch.el= is the live check of the writes: it runs every function
  of =approve-mutations.el= on #8, in order (viewed, comments on a line, a
  range and the file, replies, edits, deletes, submit, resolve, a single
  comment, discards, conversation comments), and after each one compares
  the store with #8 loaded anew from GitHub, and checks that change
  detection finds nothing new there (D23: Approve's own writes never
  count).  Run it after changing a mutation, what keeps the store true
  after one, or what change detection compares:
  #+begin_src sh
  timeout 900 cask exec emacs -Q --batch -L lisp -l dev/scratch.el \
    -f approve-scratch-run-batch > /tmp/scratch.log 2>&1
  grep -E '^(PASS|FAIL|ERROR)' /tmp/scratch.log
  #+end_src
  It sends requests through the =gh= CLI (=approve-scratch-gh-transport=),
  so it needs =gh auth login= with write access, not ghub's token.  It
  refuses to start while the viewer has a pending review on #8, and
  deletes what it wrote except the reviews it submitted (GitHub keeps
  those).  Add a step for each new mutation.

* Debugging
- =M-x approve-dev-offline-mode= serves fixtures instead of GitHub.
- =approve-log-level= =debug= logs every request with its cost and timing to
  =*approve-log*=.
- =approve-dev-inspect-query= shows a query with includes expanded.
- =approve-dev-model-dump= shows the store of the current PR buffer.
- =approve-dev-benchmark= times the speed budgets with the fixtures (compile
  first: =make build=; uncompiled code is about four times slower).
- Altair or =verb= (see approve-old's =graphql.org=) for trying queries by hand.
