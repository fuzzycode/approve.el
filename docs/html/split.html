What it means D05 · architecture.org › Data model

Today one PR buffer holds everything, the diff last. The split layout moves the Diff section out into a second buffer, *approve-diff: fuzzycode/approve#1234*, linked to the first. The PR buffer becomes an overview: header, pending review, description, checks, commits, conversation and the file list. Nothing is copied: the diff buffer points at the overview's store (approve-model-store-buffer, as the file view already does), so a comment, a reply or a viewed mark made in either buffer redraws both.

 └──────────────────────────────┘                     one store, one session: a change redraws both

Both layouts are the same sections over the same store; only which buffer runs approve-insert-diff-section differs. approve-layout picks the default for new PRs, L switches the PR at hand.

Not GitHub's “split” diff. GitHub's Files changed tab has a Unified / Split switch that puts the old and new code in two columns. That is a different feature, and not planned: Approve's diff stays unified (D12's parsed patches), and the file view (F, b for the other version) is where a file is read whole. “Split” here means the diff in its own buffer, as Magit splits its status and diff buffers.

What it is good for

Gains

  • Talk and code side by side. The conversation or a review's summary on the left, its threads open on the right. RET on “@bob approved · 3 comments on code” shows them in the diff without moving the overview.
  • Two places, two points. Each buffer keeps its own point, scroll and folds. Reading the conversation no longer means leaving your place in a 3 000-line diff and finding it again.
  • The file list becomes a navigator. Progress (viewed, threads) on one side, the code on the other.
  • Search where you mean. C-s, occur, consult-line in the diff buffer hit only code and threads; in the overview, only the discussion.
  • Room. The diff in a wide window, its own frame, tab or monitor; the overview short and quick to move in.
  • Familiar. Magit's status and diff buffers; GitHub's Conversation and Files changed tabs.

Costs

  • Two buffers to place, and people disagree on windows: the display needs an option, as the file view has (approve-file-display-action).
  • Every jump that now moves inside one buffer must learn to cross to the other: ]u [u ]t [t, j n, j /, RET on a pending comment or a review, RET back from a file view, and the input buffer's highlighted target lines.
  • One more key, from a file in the list to its diff, as RET opens the file whole today.
  • Speed: diff bodies are already drawn lazily, so the split mostly helps ergonomics; a store change still redraws both buffers.

What it looks like a wide frame · approve-page-width 80 in the overview

The overview on the left, the diff on the right, chosen by the display action when the frame is wide. Point is in the diff, on a line with threads. The overview marks the file the diff is on proposal, and its file list says which files are viewed, with the count on its heading open: in the split layout it is where you steer from. The diff buffer's header line names the PR and what the diff shows (Phase 10 names a review range there).

  • The folds come along: what was folded in the Diff section is folded in the diff buffer, and back (each buffer has its own visibility cache, so L carries it over).

Open questions

What the docs don't settle yet. A recommendation is marked →.

1. The key from a file in the list to its diff

RET on a file opens it whole today, in the list and on the diff's heading (Phase 6).

→ a. RET goes one step deeper, in both layouts: in the list to the file's diff (in the single layout, a few lines down), on the diff's heading or a line to the whole file, in the file view back to the diff. F (gf) opens it whole from anywhere. Changes the list's RET.

b. RET to the diff in the split layout only; the single layout keeps it as today. The same row does two things depending on the layout.

c. A new key, = (“diff”, as in Dired, Ibuffer and VC), evil g=; RET unchanged.

2. Where the diff buffer shows

→ Beside the overview when the frame is wide enough, else in the same window; a window that shows it already is reused. approve-diff-display-action changes it, as approve-file-display-action does for the file view.

Alternatives: always the same window (Magit's traditional way), or always a window to the right.

3. Viewed marks in the file list

ui.org says the list doesn't show which files are viewed: the diff's headings do, a few lines below. In the split layout the diff is elsewhere and the list is the navigator.

→ In the split layout, the list shows ✓ · ↻ and its heading “4/12 viewed”; the single layout stays as it is. v already works on a file in the list.

Or in both layouts, or in neither.

4. Does the overview follow the diff?

→ The overview marks the file the diff buffer's point is in (a highlight on its row, cheap, no scrolling). Nothing moves by itself.

More: moving in the list scrolls the diff to the file under point (as Magit's log follows into its revision buffer), behind an option.

5. The way back, for evil

^ is evil's first-non-blank motion, and Approve's evil keys never shadow motions.

→ q is enough (it quits the diff's window), with J f for the file list; no new evil key.

Or a key for “the overview at this file”, such as gO.

6. What the diff buffer holds

→ The Diff section only, from its own hook (approve-diff-sections-hook), so a user can add the pending review above it with approve-add-section-hook.

Or “Your pending review” on top by default, so S's context is in view while reviewing.
