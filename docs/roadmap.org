#+title: Roadmap

Phases are ordered so that each one ends with something usable and builds
only on finished layers.  Each phase has tasks, a definition of done, and the
flows ([[file:flows.org][F..]]) and mockups ([[file:ui.org][ui.org]]) it implements.  Spikes (SP..) are
short experiments that answer an open question before the phase that needs
it; write the answer into [[file:decisions.org][decisions.org]].

Agents: pick the first unchecked task of the current phase, read the docs it
links, do it in small commits ([[file:development.org][development.org]]), tick it here.

* Definition of done (every task)
- Byte-compiles with no warnings; =make lint= is clean (package-lint, checkdoc).
- Behaviour tests exist and pass (=make test=); no network in tests.
- Every new face is in =approve-faces.el= and inherits; every icon goes
  through =approve-icon=; every user-visible string can be customized or
  comes from GitHub.
- Works with and without evil loaded.
- Docs updated: a changed decision, flow or mockup is changed in the same
  commit, in the org file and in its HTML view (=docs/html/=, =make docs=).

** SP1 Review API behaviour
Before =approve-review.el=, on a scratch repository, find out and note in
[[file:decisions.org][decisions.org]]:
- Can a single comment (=addPullRequestReview= with =event=) be posted while
  the viewer has a pending review?  (Expected: no.  Then =C-u c= says so.)
- Does a reply without =pullRequestReviewId= publish at once while a review
  is pending?
- Multi-line ranges: may they span hunks?  Mix LEFT and RIGHT?
- Can context lines outside hunks (expanded context) take comments?
- Deleting the last comment of a pending review: does the review remain?
- Does the =REQUEST_CHANGES= / =COMMENT= verdict need a body when there are
  no comments?  Does it need one on the viewer's own PR (where approve and
  request changes are not allowed)?

* Ideas
Not planned yet.  Each needs a decision before it enters a phase.
- Apply suggestions from Emacs with =createCommitOnBranch= (needs the
  full file contents, API-only).
- AI-assisted review in the spirit of Hutch: a gptel-backed command that reads
  the PR diff through the API and proposes comments and suggestions as
  *pending* review comments, which the user edits or deletes before
  submitting.  Nothing is ever posted without the user's submit.
- A failing check's log in a buffer (Actions REST API), with timestamps.
- Create a PR from Magit (=createPullRequest=), with a template.
- Org links to PRs, threads and comments (=approve:owner/repo#123=).
- A "review queue" mode: walk unviewed files one by one, full-screen, with
  =v= advancing to the next.
- Avatars (shr images, cached) next to authors, behind a defcustom.
