#+title: Roadmap

Phases are ordered so that each one ends with something usable and builds
only on finished layers.  Each phase has tasks, a definition of done, and the
flows ([[file:flows.org][F..]]) and mockups ([[file:ui.org][ui.org]]) it implements.  Spikes (SP..) are
short experiments that answer an open question before the phase that needs
it; write the answer into [[file:decisions.org][decisions.org]].

Agents: pick the first unchecked task of the current phase, read the docs it
links, do it in small commits ([[file:development.org][development.org]]), tick it here.

* Definition of done (every task)
- Byte-compiles with no warnings; =make lint= is clean (package-lint, checkdoc).
- Behaviour tests exist and pass (=make test=); no network in tests.
- Every new face is in =approve-faces.el= and inherits; every icon goes
  through =approve-icon=; every user-visible string can be customized or
  comes from GitHub.
- Works with and without evil loaded.
- A new command is in the dispatch transient (=?=) and the Keys table of
  [[file:ui.org::*Keys][ui.org]], with a preflight if it changes the PR ([[file:decisions.org::*D06 Menus are transients; everything is reachable from =?=][D06]]).
- Docs updated: a changed decision, flow or mockup is changed in the same
  commit, in the org file and in its HTML view (=docs/html/=, =make docs=).

** SP1 Review API behaviour
Before =approve-review.el=, on a scratch repository, find out and note in
[[file:decisions.org][decisions.org]]:
- Can a single comment (=addPullRequestReview= with =event=) be posted while
  the viewer has a pending review?  (Expected: no.  Then =C-u c= says so.)
- Does a reply without =pullRequestReviewId= publish at once while a review
  is pending?
- Multi-line ranges: may they span hunks?  Mix LEFT and RIGHT?
- Can context lines outside hunks (expanded context) take comments?
- Deleting the last comment of a pending review: does the review remain?
- Does the =REQUEST_CHANGES= / =COMMENT= verdict need a body when there are
  no comments?  Does it need one on the viewer's own PR (where approve and
  request changes are not allowed)?
- Found (2026-11-13) :: on fuzzycode/test-approve, written up as [[file:decisions.org::*D32 Reviews are written the way GitHub's API allows (SP1)][D32]].
  No single comment while a review is pending.  A reply without the review
  id joins the pending review, and is published at once only when none is
  pending.  Ranges may mix sides and even span hunks (Approve keeps them in
  one).  Lines outside the hunks take no comment, and GitHub answers with
  a null thread, not an error.  Deleting the last pending comment deletes
  the review.  Comment and Request changes need a body or comments, Approve
  needs neither; on one's own PR, Approve and Request changes are refused.
  Comments, replies, submit and discard need only the PR's id.

** SP7 Applying suggestions
GitHub has no API for its "Commit suggestion" button.  On the scratch
repository, find out and note in [[file:decisions.org][decisions.org]]:
- What commit message and =Co-authored-by= trailer GitHub's button
  writes, and where the suggester's e-mail comes from (their noreply
  address needs the user's =databaseId=).
- Whether =createCommitOnBranch= can write to a fork's branch that allows
  edits from maintainers, and what =viewerCanApplySuggestion= says there.
- What GitHub does to the thread when its suggestion is committed
  (resolved?), and whether committing through the API does the same.
- Multi-line suggestions, an empty suggestion (deletes the lines),
  outdated threads, and a suggestion whose lines changed since.
- Line endings and the file's last newline, kept as they were.
- Found (2026-11-15) :: on fuzzycode/test-approve #10, written up as
  [[file:decisions.org::*D41 Suggestions are committed the way GitHub's button does (SP7)][D41]].  GitHub's button and =createCommitOnBranch= make the same
  commit (the viewer the author, GitHub the committer, signed by
  web-flow); the message defaults to "Apply suggestion from @login" or
  "Apply batched suggestions from code review", with a =Co-authored-by=
  trailer per suggester, whose noreply address
  (=DATABASEID+LOGIN@users.noreply.github.com=) GitHub attributes.  The
  button resolves its threads; the API leaves them outdated, so Approve
  resolves them.  Line endings and a missing final newline are kept, an
  empty suggestion deletes its lines, threads below move without going
  outdated.  Each suggestion block has its own button, also in replies;
  none on pending comments, outdated or file-level threads, deleted
  lines, or no change.  =viewerCanApplySuggestion= stays true on closed
  and merged pull requests.  Forks with maintainer edits are not checked
  (no second account).

** SP8 The clone and its lines
On a clone of the scratch repository, find out and note in
[[file:decisions.org][decisions.org]] (the part D36 left open):
- How a PR finds its clone, starting from D37's list: the current project
  (=project.el=), a clone whose remote is the repository (ssh or https,
  Enterprise hosts), or an option mapping repositories to directories;
  several clones or worktrees of one repository.
- How a branch finds its PR: =headRefName= and the head repository
  (forks), the branch's upstream, several PRs from one branch, a closed or
  merged PR.
- Which blob to diff against the buffer when the local HEAD is the PR's
  head, ahead of it (commits not pushed), behind it (pushed from
  elsewhere) or on another history (rebased), and when to say the clone
  and GitHub differ.
- What a diff of the buffer costs on a large file, per edit, so the marks
  keep up with typing (the budgets in [[file:architecture.org::*Speed][architecture.org]]).
- Outdated threads: shown where they were (=originalLine= at
  =originalCommit=), or only listed.
- Whether the mode turns itself on (a global mode, =find-file-hook=), and
  what that costs in a clone with no PR.
- Found (2026-11-16) :: on a clone of the scratch repository with four
  worktrees, #15 and #16, written up as [[file:decisions.org::*D45 A branch has the PR; its threads are placed by a diff of the text (SP8)][D45]].  A clone is found by its
  remotes, read from its =config= file (2 ms for 37 clones); one
  =for-each-ref= gives each branch's upstream, push branch and worktree.
  A branch, not a clone, has the PR: the head repository's ref's
  =associatedPullRequests= finds it, a fork's into its parent too, and
  =headRefName= finds one whose branch is gone, in one query of cost 1.
  A =diff= of the file at the PR's head against the buffer's text places
  every thread whether the clone is at GitHub's head, ahead, behind or
  diverged; the state is only said.  The diff in an asynchronous process,
  on temporary files, keeps Emacs busy under 10 ms at 200 000 lines
  (40 ms until the hunks).  Outdated threads, mapped from their
  original commit, land on the line that replaced them.  A global mode
  costs about 14 ms of git for the first file of a clone and branch, and
  one query a branch.  The author chose: D37's list alone, the file view
  when no clone has the branch, outdated threads and threads on removed
  lines shown where they were, an opt-in global mode for open PRs, and
  the newest open PR of a branch, switchable.

* Phase 13 — AI agents, plugged in
AI agents on both sides of a pull request: getting feedback on one (an
agent's review of your PR before people see it, and help with theirs:
threads summed up, replies drafted, the code they ask for changed in
your clone, [[*Phase 7 — Review feedback in your clone][Phase 7]]) and reviewing one (an agent reads the PR and
proposes comments and suggestions, which the reviewer keeps, edits or
drops).  Added (2026-11-16) at the author's request, last, with nothing
designed yet: a design deep dive decides how when the phase comes, and
writes its tasks.  An idea moved here from [[*Ideas][Ideas]] as a starting point:
AI-assisted review in the spirit of Hutch, a gptel-backed command that
reads the diff through the API and proposes comments and suggestions as
pending review comments, which the user edits or deletes before
submitting; nothing is posted without the user's submit.  Two things
are settled already.  Approve works fine without AI: no AI package is
required ([[file:decisions.org::*D25 Dependencies][D25]]), and with no agent plugged in nothing about AI shows,
runs or slows Approve down.  And an agent is something the user plugs in
if they want one, which is easy to do.
- [ ] Design deep dive with the author, before any code.  To answer:
      - What agents do on each side.  For the author: feedback before
        people review, and a review's threads summed up, answered or
        fixed.  For the reviewer: the PR summed up, comments and
        suggestions proposed, questions about the diff answered.  Which
        come first.
      - What an agent is to Approve: an Emacs package (gptel, llm), a
        coding agent run as a process (its CLI), or Approve's PR offered
        to an agent the user runs elsewhere (an MCP server); which of
        them work out of the box.
      - How one is plugged in: what the user sets, the hooks and
        functions the core offers (as =approve-visit-commit-functions=,
        [[file:decisions.org::*D37 Clones are found where Magit lists them; a commit opens in Magit][D37]]), and modules apart that the core never requires, as the
        clone's are ([[file:decisions.org::*D36 No clone needed; a local clone adds to it][D36]]).
      - What an agent reads (the store, the files at the head, a clone)
        and what it may write: drafts and pending comments that only the
        user's submit publishes (the starting point's answer, [[file:decisions.org::*D02 Durable state lives on GitHub][D02]]), or
        more.
      - Where its work shows (the PR buffer, input buffers, a buffer of
