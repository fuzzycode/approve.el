#+title: Roadmap

Phases are ordered so that each one ends with something usable and builds
only on finished layers.  Each phase has tasks, a definition of done, and the
flows ([[file:flows.org][F..]]) and mockups ([[file:ui.org][ui.org]]) it implements.  Spikes (SP..) are
short experiments that answer an open question before the phase that needs
it; write the answer into [[file:decisions.org][decisions.org]].

Agents: pick the first unchecked task of the current phase, read the docs it
links, do it in small commits ([[file:development.org][development.org]]), tick it here.

* Definition of done (every task)
- Byte-compiles with no warnings; =make lint= is clean (package-lint, checkdoc).
- Behaviour tests exist and pass (=make test=); no network in tests.
- Every new face is in =approve-faces.el= and inherits; every icon goes
  through =approve-icon=; every user-visible string can be customized or
  comes from GitHub.
- Works with and without evil loaded.
- A new command is in the dispatch transient (=?=) and the Keys table of
  [[file:ui.org::*Keys][ui.org]], with a preflight if it changes the PR ([[file:decisions.org::*D06 Menus are transients; everything is reachable from =?=][D06]]).
- Docs updated: a changed decision, flow or mockup is changed in the same
  commit, in the org file and in its HTML view (=docs/html/=, =make docs=).

** SP1 Review API behaviour
Before =approve-review.el=, on a scratch repository, find out and note in
[[file:decisions.org][decisions.org]]:
- Can a single comment (=addPullRequestReview= with =event=) be posted while
  the viewer has a pending review?  (Expected: no.  Then =C-u c= says so.)
- Does a reply without =pullRequestReviewId= publish at once while a review
  is pending?
- Multi-line ranges: may they span hunks?  Mix LEFT and RIGHT?
- Can context lines outside hunks (expanded context) take comments?
- Deleting the last comment of a pending review: does the review remain?
- Does the =REQUEST_CHANGES= / =COMMENT= verdict need a body when there are
  no comments?  Does it need one on the viewer's own PR (where approve and
  request changes are not allowed)?
- Found (2026-11-13) :: on fuzzycode/test-approve, written up as [[file:decisions.org::*D32 Reviews are written the way GitHub's API allows (SP1)][D32]].
  No single comment while a review is pending.  A reply without the review
  id joins the pending review, and is published at once only when none is
  pending.  Ranges may mix sides and even span hunks (Approve keeps them in
  one).  Lines outside the hunks take no comment, and GitHub answers with
  a null thread, not an error.  Deleting the last pending comment deletes
  the review.  Comment and Request changes need a body or comments, Approve
  needs neither; on one's own PR, Approve and Request changes are refused.
  Comments, replies, submit and discard need only the PR's id.

** SP7 Applying suggestions
GitHub has no API for its "Commit suggestion" button.  On the scratch
repository, find out and note in [[file:decisions.org][decisions.org]]:
- What commit message and =Co-authored-by= trailer GitHub's button
  writes, and where the suggester's e-mail comes from (their noreply
  address needs the user's =databaseId=).
- Whether =createCommitOnBranch= can write to a fork's branch that allows
  edits from maintainers, and what =viewerCanApplySuggestion= says there.
- What GitHub does to the thread when its suggestion is committed
  (resolved?), and whether committing through the API does the same.
- Multi-line suggestions, an empty suggestion (deletes the lines),
  outdated threads, and a suggestion whose lines changed since.
- Line endings and the file's last newline, kept as they were.
- Found (2026-11-15) :: on fuzzycode/test-approve #10, written up as
  [[file:decisions.org::*D41 Suggestions are committed the way GitHub's button does (SP7)][D41]].  GitHub's button and =createCommitOnBranch= make the same
  commit (the viewer the author, GitHub the committer, signed by
  web-flow); the message defaults to "Apply suggestion from @login" or
  "Apply batched suggestions from code review", with a =Co-authored-by=
  trailer per suggester, whose noreply address
  (=DATABASEID+LOGIN@users.noreply.github.com=) GitHub attributes.  The
  button resolves its threads; the API leaves them outdated, so Approve
  resolves them.  Line endings and a missing final newline are kept, an
  empty suggestion deletes its lines, threads below move without going
  outdated.  Each suggestion block has its own button, also in replies;
  none on pending comments, outdated or file-level threads, deleted
  lines, or no change.  =viewerCanApplySuggestion= stays true on closed
  and merged pull requests.  Forks with maintainer edits are not checked
  (no second account).
