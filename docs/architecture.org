#+title: Architecture

How Approve is put together: layers, modules, data, network, rendering, errors
and speed.  Decisions referenced as D.. are in [[file:decisions.org][decisions.org]].

* Layers
Code depends downwards only.  A layer never calls one above it, except through
callbacks it was given.

Rules:
- Renderers never call the network and never change the store.  Given the same
  store, they insert the same text.
- Operations never touch buffers.  Callbacks run in the originating buffer
  (=approve-api=), so the store they patch is that buffer's.
- Actions are the only place where context, input, network and redraw meet.
- Nothing outside =approve-api.el= calls ghub.
- Only the modules for a local clone touch one (its files, branch, git), and
  the core never requires them: every other module works without a clone
  (D36).  =approve.el= requires them and puts their functions on the hooks
  the core offers, such as =approve-visit-commit-functions= (D37), and the
  core's buffer-local functions say what a clone's buffer holds
  (=approve-context-function=, =approve-diff-range-positions-function=).
  =approve-feedback.el= sits at the top, as it arranges the core's commands
  in its map and dispatch; its own buffers' code is the Buffers layer's.

* Data model
The store from approve-v2 (D10), with a few additions.

#+begin_example
 buffer-local
 ┌───────────────────────────────────────────────────────────────────────┐
 │ approve-model--store   typename → id → alist                          │
 │   "PullRequest"        "PR_kw…"   → ((title . "…") (author . REF) …)  │
 │   "User"               "U_kg…"    → ((login . "bob") (name . "Bob") …)│
 │   "PullRequestReviewThread" "PRRT_…" → ((path . "…") (line . 42)      │
 │                                         (comments . ((nodes REF REF)  │
 │                                                      (totalCount . 2))│
 │   "IssueComment" …   "PullRequestReview" …   "Label" …   "Commit" …   │
 ├───────────────────────────────────────────────────────────────────────┤
 │ approve-model--root    REF to the PullRequest                         │
 ├───────────────────────────────────────────────────────────────────────┤
 │ approve-model--meta    :host :owner :repo :number :viewer             │
 ├───────────────────────────────────────────────────────────────────────┤
 │ approve-model--extra   data without node ids, keyed by name:          │
 │   :patches   path → parsed patch (from REST)                          │
 │   :range     the commit range under review (nil = all changes)        │
 ├───────────────────────────────────────────────────────────────────────┤
 │ approve-session        UI state, never sent anywhere:                 │
 │   :loading   set of section keys still loading                        │
 │   :errors    section key → error                                      │
 │   :inflight  the actions in flight, (N . MARKS): what each one marks  │
 │   :drafts    target → unsent text (survives C-c C-k, lost on kill)    │
 │   :layout    single | split                                           │
 │   :threads   folded | shown, once T folded or unfolded every thread   │
 │   :changes   what differs on GitHub, from the last check (D23)        │
 │   :checking :checked   a check is out · when the last one was sent    │
 │   :suggestions  the batch of suggestions, each (COMMENT-ID . INDEX)   │
 └───────────────────────────────────────────────────────────────────────┘
#+end_example

- A REF is =(:approve-ref TYPENAME ID)=.  =approve-model-get= resolves refs on
  read.
- Connections become =((nodes …) (totalCount . N) (pageInfo …))= or a plain
  list when no paging info was asked for.
- Selectors are the only way renderers read data, e.g.
  =(approve-pr-threads-for-file PATH)=, =(approve-pr-pending-review)=,
  =(approve-pr-files)=, =(approve-pr-viewer-can 'update)=,
  =(approve-pr-new-p NODE)= (new since the viewer's last review, D44).
  Selectors hide the store layout so it can change.
- List edits for creations and deletions:
  =(approve-model-append-ref OWNER-REF FIELD REF)=,
  =(approve-model-remove-ref OWNER-REF FIELD REF)=, and
  =(approve-model-edit-list OWNER-REF FIELD FUNCTION)= for anything else
  (a file's viewed state).  The mutations make them, after patching the
  store with GitHub's answer ([[file:decisions.org::*D35 Mutations keep the store true: GitHub's answer, then list edits][D35]]); =approve-model-raw-field= reads
  the store as it is stored, refs unresolved, for walking it cheaply.
- The PR buffer and the split diff buffer share one store: the diff buffer
  points to its PR buffer (=approve-model-store-buffer=), and every model
  function reads and writes the store and session there.  A file view
  (=approve-file.el=) points to its PR buffer the same way.
- The dashboard and search lists do not normalize; they keep the raw search
  result (it is shown once and thrown away).  The pull requests opened in
  the session, newest first, are a global list in =approve-pr.el=
  (=approve-pr-recent=, D39); the dashboard asks GitHub for their rows.
- Extended details for eldoc (a user's bio, an issue's title, a commit's full
  message) live in one global cache, =approve-eldoc--details=, keyed by host,
  type and id, for the Emacs session.  They are shared by every Approve
  buffer; =C-u g= clears them.
- Repository metadata (D24: mentionable and assignable users, labels, open
  milestones, the owner's teams, the issues and PRs updated last, emoji)
  lives in =approve-metadata.el='s global cache, keyed by API
  host, repository and kind (emoji by host only), for the Emacs session.
  It never enters the store; =C-u g= clears it.
- The texts of files the file view fetched live in =approve-file.el='s
  global cache, keyed by host, repository, commit and path, for the Emacs
  session (a commit's file never changes); =C-u g= clears them.

* Loading a PR
Several smaller queries in parallel instead of one huge one: the header shows
quickly and each section fills in when its data arrives.

#+begin_example
 time ─────────────────────────────────────────────────────────────────────▶
 open   skeleton drawn: title from URL, every section shows "Loading…"
  │
  ├─ Q core ─────────▶ header, metadata, description, status, pending review
  ├─ Q files ───────────▶ file list + viewed state            (pages of 100)
  ├─ Q threads ───────────────▶ inline threads, unresolved count (pages)
  ├─ Q timeline ────────────────▶ conversation                  (pages)
  ├─ Q commits ──────▶ commits section
  └─ R patches ───────────────────────▶ diff bodies             (pages of 100)
        each arrival: normalize → store → schedule redraw (coalesced ≈50 ms)
        an error marks only its own section: "✗ … · g to retry"
        (Q core failing, or a token error from any query: the whole buffer
        shows that one error, and the echo area says it)
#+end_example

- Pagination: =approve-api-graphql-all= follows =pageInfo.endCursor= and
  patches each page into the store as it arrives, so long lists render
  progressively.  Nested connections (comments in a thread) beyond the first
  page show "Load N more" and are fetched on demand.
- Large files: when REST omits =patch= (too big), the file section says so and
  offers "Load diff": fetch both blobs (base and head oid) and diff them
  locally (=diff-no-select=, or =diff= on temp files).  Binary files show only a
  heading.
- =g= reruns the same plan and keeps the buffer as it is until data arrives.
  A refresh is atomic per query: a list's pages are collected and replace
  the old list together, so it never shrinks to its first page meanwhile.
- The session tracks each query under its key (=core=, =files=, =threads=,
  =timeline=, =commits=, =patches=, =checks=): =:loading=, =:loaded=,
  =:errors=.  Sections read it to show "Loading…" or their error.
- Data that only an expanded section shows (the check contexts) is loaded
  after the command that expanded it (=approve-pr-lazy-loaders=), and again
  on =g= once it was loaded.

* Rendering
** Section tree of the PR buffer
Single layout (D05).  In the split layout, =approve-diff= moves to the diff
buffer, which the file list opens at a file (its key is chosen with F18).

 ├── approve-header-section          metadata rows (number, title, state: header line)
 │   └── approve-meta-section *      (value: author, repository, branch, opened, reviewers, …, status)
 ├── approve-pending-review-section  only when the viewer has a pending review (value: review id)
 │   └── approve-pending-comment-section *  (value: comment id)
 ├── approve-description-section
 │   └── approve-html-details *      <details> in the body (value: (index . summary))
 ├── approve-checks-section          collapsed; contexts load when first expanded
 │   ├── approve-check-section *     (value: check id)
 │   └── approve-checks-more-section "… N more passed"
 ├── approve-commits-section         collapsed
 │   └── approve-commit-section *    (value: oid)
 ├── approve-conversation-section
 │   └── approve-issue-comment-section * | approve-review-section *
 │       | approve-event-section *     (value: node id of the first item of a run)
 ├── approve-files-section           file list with stats; not shown by default (D05)
 │   └── approve-file-entry-section * (value: path)
 └── approve-diff-section
     └── approve-file-section *      (value: path)        collapsed; body inserted lazily
         ├── approve-file-threads-section   (value: file) file-level threads
         ├── approve-hunk-section *  (value: (path . "@@ -a,b +c,d @@ …"))
         │   └── approve-line-section *  (value: (path side line))  only lines with threads; folds them
         │       └── approve-thread-section *  (value: thread id)  does not fold by itself
         │           └── approve-comment-section * (value: comment id)
         └── approve-file-threads-section   (value: outdated) collapsed
#+end_example

- Section classes are EIEIO subclasses of =magit-section=; their type is the
  class name.  A =keymap= slot can make keys depend on what point is on
  (thread keys on threads, file keys on files) once commands need it.
- Bodies are indented by decoration text (=approve-render-prefix=), which
  copying leaves out and which nests: a thread's bar sits inside its line's
  indentation.  Never by display-only =line-prefix=: a collapsed body would
  lend it to the next heading (D28).
- Every section value is stable across redraws, so the visibility cache and
  point restore work (D13).
- Inserting a section only records whether it is collapsed; after drawing,
  =approve-pr-redraw= calls =magit-section-show= on the root, as
  =magit-refresh-buffer= does, which hides the bodies of collapsed sections.
- Diff lines without threads are plain text with a text property
  =approve-line= = =(:path P :side LEFT|RIGHT :old N :new M :kind add|del|ctx)=.
  Only lines with threads become sections, which keeps the section count low.
- Diff bodies use =magit-insert-section-body=, so collapsed files cost nothing.
- Thread index: a hash of =(side . line)= → threads, built for a file when
  its body is drawn (=approve-diff-thread-index=).  A thread sits under the
  line its =diffSide= and =line= name (the end of a range; a =LEFT= thread
  under a removed or context line by its old number).  File-level threads go
  to "On this file", threads whose line is not in the current diff to
  "Outdated" under the file.
- Parsed patches are cached by patch string (weakly), so a redraw never
  parses again.

** Rendered HTML
=approve-html-render= turns a =bodyHTML= into a string with faces, at column
0 and =approve-fill-column= wide; callers indent it.  Strings are cached by
HTML and width, so a redraw only inserts them.  Links carry =approve-url=,
and mentions, team mentions, issue links and commit links also carry
=approve-thing= (=(:kind user :login …)=, =(:kind ref :owner :repo :number)=,
…) for the context and eldoc.  A suggested change's box carries
=(:kind suggestion :index N)=: it is the Nth suggestion of the HTML, from
0, as the markdown's Nth suggestion block is.  =approve-html-insert= turns each top-level
=<details>= into an =approve-html-details= section (value: index and
summary, so it is stable).

Images: the renderer draws an image from =approve-html='s image cache, or a
placeholder link and adds the URL to =approve-html-wanted-images=.  The
buffer fetches wanted images after a redraw, hands each to
=approve-html-put-image= and redraws, so the renderer never touches the
network.

* Input buffers
- =approve-input-read= (from approve-v2) opens a buffer in
  =approve-input-mode= (=gfm-mode=) below the current window
  (=approve-input-display-action=) and returns it.  =:prompt= says what the
  text is for and =:context= where it goes; both start the header line, with
  the keys at its right edge.  =:name= names the buffer, =:initial= fills
  it, =:single-line= makes RET send one line (a title), as =C-c C-c= does
  and the header line says, =:allow-empty= lets
  an empty text be sent (a review body), =:commit-label= says what =C-c C-c=
  does ("send", "submit").  =:on-commit= gets the text and =:on-abort=
  nothing, both in the buffer the input was opened from, after the input's
  window is gone.
- =approve-input-with-submit-key= wraps every minibuffer prompt of Approve
  where =RET= submits (pickers, reasons, reactions, a file, the URL of
  =M-x approve=): =C-c C-c= runs there what =RET= runs, so it applies and
  sends everywhere (D40), whatever the completion UI.
- =:target= is a stable key for drafts, such as =(reply "PRRT_1")=.  Abort
  keeps the text in the session's =:drafts= under the target, and so does
  killing the input buffer; reopening the same target fills the buffer from
  the draft.  A sent text stays the draft too, until the action drops it
  with =approve-input-clear-draft= once GitHub has it (F00), so a failed
  request loses nothing.  A blank text, or the unchanged =:initial=, drops
  the draft.  Killing the PR buffer drops drafts (D02 allows this).
  An input already open for a target is shown again rather than doubled.
- =:lines= is the range of diff lines the text is about (a =line= or
  =lines= context).  They stay highlighted (=approve-target=, an overlay
  per line) in the buffer the input was opened from, put back after each
  redraw, until the text is sent or aborted.  =approve-diff-range-positions=
  finds where a range is drawn, =approve-diff-range-lines= its lines in the
  patch.
- Evil users start in insert state (=approve-evil.el=).
- Completion at point (=approve-input-completion-at-point=): =@user= (the
  people the store holds, the PR's author first, then the repository's
  mentionable users; never the viewer), =#123= (the issues the PR closes,
  then the 100 issues and PRs updated last, annotated with title and
  state), =:emoji:= (GitHub's, with their glyphs; the colon is closed).
  Nothing completes right after a letter or digit, so e-mail addresses and
  URLs are left alone.  =C-c @= inserts a mention through =completing-read=.
  The lists other than the store's are repository metadata (D24,
  =approve-metadata.el=): opening an input buffer (not a single line)
  fetches them in the background unless they are cached, as a completion
  function can't wait for the network.
- =C-c C-p= shows the text as GitHub will: =approve-query-markdown= sends
  it to REST =/markdown= (=gfm=, in the PR's repository, read as text), and
  =approve-html= draws the answer in a window beside the input
  (=approve-input-preview-display-action=, a side window).  It is asked for,
  not live; the preview closes with its input.
- =C-c C-s= inserts a ```suggestion``` block holding the new side of
  =:lines= (their added and context lines, from the patch), with point at
  the end of its last line; =:suggest= starts the text with it (F06).  On
  removed lines alone, or with no lines, it says why it can't.  The header
  line offers it while the text is on code and has no suggestion yet.

* Actions
Every command that changes something on GitHub runs the action pipeline
([[file:flows.org::*F00 The action pipeline][F00]]), in =approve-actions.el=; the commands are in =approve-commands.el=
and, for the pending review as a whole, =approve-review.el=; those of the PR's
metadata are in =approve-manage.el=.  A command
supplies its own parts (the ✱ of F00) and nothing else:

#+begin_example
 (defun approve-commands--resolve-preflight ()        what it acts on, or why not
   (let* ((context (approve-action-context            (a user-error); changes nothing
                    '(thread) "Put point on a thread"))
          (id (plist-get context :thread-id)))
     (unless (plist-get context :can-resolve)
       (user-error "You can't resolve this thread"))
     id))
 (put 'approve-resolve 'approve-preflight #'approve-commands--resolve-preflight)

 (let ((id (approve-commands--resolve-preflight)))
   (approve-action-run
    :what "resolve the thread"                       for "could not resolve the thread: …"
    :input nil                                       or approve-input-read's arguments
    :marks `((section approve-thread-section ,id))   what waits for GitHub
    :send (lambda (_text callback errorback)         queue the mutations
            (approve-mutation-resolve-thread id :callback callback :errorback errorback))
    :done (lambda (result) …)))                      anything else, before the redraw
#+end_example

- The /preflight/ comes first: what the command acts on, or a =user-error=
  saying why it can't run here (nothing it applies to at point, no
  =viewerCan*=).  It must change nothing, as the menus call it too: the
  =approve-preflight= property names it, and =approve-action-why-not=
  gives its reason, which dims the command in the dispatch ([[file:decisions.org::*D06 Menus are transients; everything is reachable from =?=][D06]]).
- =approve-action-context= is the context at point when the command
  applies to its kind (a list of kinds, or a predicate), else the context
  of the section around point if the command applies to that (on a
  comment's =@author=, =r= replies to the comment), else a =user-error=
  with what the command needs.  It also refuses where no pull request has
  loaded.
- Where threads are drawn under the lines, point is never on one, and
  the commands of threads and comments reach their preflight through
  =approve-action-target=: when it refuses the line itself, it is tried on
  each of the line's =:threads=, then on each of their comments, and the
  command acts on the one it takes, asking which (=completing-read=) when
  it takes several.  The menus ask the same, quietly
  (=approve-action-why-not=), so =r= is dimmed on a line without threads
  ("No threads on this line") and =e= where none of the comments is
  yours.
- =approve-action-run= signals =:why-not= as a =user-error= (for a reason
  only known once the command has started, such as a verdict GitHub
  refuses), then asks for
  the text when there is =:input= (aborting stops there, keeping the
  draft).  It marks =:marks= in flight and calls =:send= in the PR buffer
  with the text (or nil), a callback and an errorback.  =:send= queues the
  mutations through the operations (=approve-mutations.el=), which patch
  the store with GitHub's answers and make the list edits ([[file:decisions.org::*D35 Mutations keep the store true: GitHub's answer, then list edits][D35]]), and
  calls the callback with a result once GitHub has confirmed them all.
- On success the input's draft goes, =:done= runs with the result (for
  what is not the store's, such as where point goes), then
  the marks go and every buffer of the PR redraws, point kept.  On failure
  the marks go and the echo area says what could not be done and GitHub's
  message (and when a rate limit resets); the text stays a draft.  The
  marks go even when =:send= or =:done= signals.
- A mark is =(section TYPE VALUE)=, the heading of each section of TYPE
  with VALUE, or =(lines RANGE)=, the diff lines of a =line= or =lines=
  context.  Marked lines take =approve-inflight=, and the loading icon
  follows the heading, or the last of the lines.  They are overlays, put
  back after each redraw (=approve-pr-redraw-hook=), so renderers know
  nothing of them.  Each action keeps its own entry in the session's
  =:inflight=, so two actions on one target don't clear each other.

* Extended information (eldoc)
[[file:decisions.org::*D27 Extended information through eldoc: one line, then the eldoc buffer][D27]]; mockups in [[file:ui.org::*Eldoc][ui.org › Eldoc]]; flow in [[file:flows.org::*F20 Look up details][F20]].

#+begin_example
 eldoc (idle, or K)
   │
   ▼
 approve-eldoc-function (callback)
   │  ctx = approve-context-at-point            no ctx → nil (other eldoc functions run)
   ▼
 describer for ctx :kind  (user, team, label, commit, ref, check, file, thread, …)
   │  echo  = one line from the store            ── never waits
   │  doc   = store data + cached details
   ▼
 details missing  and  (K was pressed  or  the eldoc buffer is visible)?
   │ no                                       │ yes
   ▼                                          ▼
 (callback doc :echo echo :thing …)         return t; query the details (async)
                                              │  cache result (or the error)
                                              ▼
                                            (callback doc+details :echo echo …)
                                            eldoc drops it if point has moved on
#+end_example

- One function, =approve-eldoc-function=, on the buffer-local
  =eldoc-documentation-functions= of every Approve buffer (PR, diff, file,
  dashboard, search, notifications).  It returns nil where it has nothing, so
  other eldoc sources (flymake, etc.) still work.
- Describers are small functions per context kind, in a table
  (=approve-eldoc-describers=), so a new kind is one entry.  Each is called
  with the context and the cached details (or nil) and returns
  =(:echo STRING :doc STRING :details (KIND . KEY))=; =approve-query-details=
  runs the query for =(KIND . KEY)= (=graphql/queries/details/=).
- Moving point around never touches the network: missing details are fetched
  only when the user presses =K= (=approve-show-details=, which fetches, then
  shows the eldoc buffer) or while the eldoc buffer is visible.  Meanwhile
  the eldoc buffer says "⟳ loading details…"; when they arrive, eldoc runs
  again (=eldoc-print-current-symbol-info=), so it documents wherever point
  is by then.  Each eldoc call answers synchronously, as the protocol wants.
- A failed detail query is cached as an error for a minute, and the eldoc
  buffer says "details unavailable (…)".  The echo line is unaffected.
- The eldoc buffer text uses Approve's faces, and URLs are buttons: =RET=
  opens them.
- Needs eldoc 1.14 for =:echo= ([[file:decisions.org::*D25 Dependencies][D25]]).

* Speed
Budgets, measured with fixtures (=approve-dev-benchmark=) in Phase 1 and kept
in CI as soft checks (=tests/test-speed.el= fails only past six times a
budget).  Measured 2026-11-08, byte-compiled, Emacs 31.1 on an Apple M-series
laptop, mean of 20 runs after a warm-up, garbage collection included
(remeasured 2026-11-09, after the redraw started detaching the old sections'
markers and hiding the bodies of collapsed sections):
| Case                                                                        | Budget               | Measured            |
|-----------------------------------------------------------------------------+----------------------+---------------------|
| Redraw, medium PR (30 files, 1 500 diff lines, 40 comments), diff collapsed | < 30 ms              | 6.6 ms              |
| Expand one 500-line file with 5 threads                                     | < 30 ms              | 15.5 ms             |
| Redraw, large PR (300 files, 20 000 lines), all collapsed                   | < 100 ms             | 36.2 ms             |
| Keypress to input buffer for a comment                                      | < 50 ms (no network) | Phase 2             |
| A clone's buffer after an edit, on idle, 200 000-line file (Phase 7, D45)   | Emacs busy < 10 ms,  | 3.1 ms, map 49 ms;  |
|                                                                             | marks < 50 ms later  | marks: Phase 7      |

The 500-line file is the medium PR's parser.go with a synthetic patch (ten
hunks of 50 lines, changed words marked) and five threads moved onto it.
The 200 000-line buffer (14 MB, three lines edited on GitHub's side, one
more here before each run) was measured on 2026-11-17 with =approve-lines.el=:
Emacs is busy writing the buffer, and the map arrives once =diff= (about
40 ms of it) is done.
Uncompiled code is about four times slower; =M-x approve-dev-benchmark=
measures whatever is loaded.

Means: lazy bodies, a thread index built once per redraw, no per-line
sections, faces as text properties (not overlays), coalesced redraws, and
syntax highlighting only for expanded files, cached per patch (D30).  Rendered HTML is
cached by its text, and parsed patches by their string.  A redraw detaches
the markers of the sections it erases: they would stay in the buffer until
garbage-collected, and every insertion moves every marker, which made
redraw time depend on when the last collection ran.  Long lists (the files,
the diff's file headings) insert their indentation with each line rather
than indenting afterwards.  In a clone's buffers (D45), the buffer is
diffed against GitHub's file by an asynchronous process on temporary
files, after edits once Emacs is idle; never through a pipe, which
blocks Emacs for seconds on a large file.  The buffer is written as
Emacs holds it (=no-conversion=, which is UTF-8): encoding it as UTF-8
takes 54 ms at 14 MB, writing it 4 ms.  It is written once for all the
texts it is compared with, and copied first only when it holds carriage
returns, which a change is checked for as it happens: =diff='s own
=--strip-trailing-cr= takes a second at 14 MB with macOS's =diff=.

* Security and privacy
- The token comes from ghub (auth-source).  Approve never stores it.
- Debug logs redact credentials, and =approve-log-level= defaults to =warn=.
- shr renders HTML without scripts.  Remote images load only when
  =approve-load-images= is non-nil (default t; GitHub proxies them through
  camo).
- Nothing is written to disk except the optional blob cache
  (=approve-cache-directory=), keyed by object id.  Blobs never change, so the
  cache is always valid.  In a clone's buffers, the diff of a buffer
  against GitHub's file reads temporary files (D45), deleted once they
  are no longer needed: when the buffer is killed, changes its major
  mode or is no longer compared, and when Emacs exits.
